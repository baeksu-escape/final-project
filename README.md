# Git 협업 규칙

🌿 브랜치 전략
각자 기능 브랜치 → develop 브랜치 → main 브랜치

- 각자 자기 기능 브랜치에서 작업
- 기능 완성되면 develop에 머지
- develop이 안정화되면 main에 최종 머지

.gitignore 설정하기 (불필요한 파일 커밋 방지)

Commit 메시지 규칙
형식: 행위 - 내용

🔀 PR(Pull Request) 규칙
- 기능이 완성된 후에 PR

1. 일부 기능만 완성했을 때
- 연관된 기능까지 묶어서 완성후 PR
- 예) 로그인만 x -> 로그인 + 회원가입까지 완성 후 PR

2. 전체 기능을 완성했을 때
- 테스트까지 성공한 후 PR

3. 공통 작업(common)을 위해 미완성 상태로 머지가 필요한 경우
- PR 메시지에 "왜 미완성 상태로 머지하는지" 꼭 기록

---------------------------------------------------------------------------------------
1. 팀원은 각자 feature/기능명 브랜치에서 개발한다.
2. 기능 구현 및 개별 테스트가 끝나면 develop으로 PR을 요청한다.
3. 다른 팀원이 코드를 검토하고 승인하면 병합한다.
4. develop에서 충돌을 해결하고 통합 테스트를 진행한다.
5. 최종 발표 및 시연이 가능한 상태인지 검증한 후 main으로 PR을 요청한다.
6. 최종 승인 후 main에 병합한다.
------------------------------------------------------------------------------------------

## 문서 위치
| 위치 | 누가 읽나 | 내용 |
|------|-----------|------|
| `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` | AI (자동) | AI 공통 규칙 |
| `docs/ai/` | AI (작업 전) | 기능 명세, 확정·미정 사항, 웹 채팅용 붙여넣기 |
| `docs/spec/` | 사람·AI | 팀이 합의한 API 명세, 피처 정의서, DB 스크립트 |
| `docs/logs/` | 사람·AI | 작업 로그와 검수 |
| `docs/guide/` | 사람 | 바이브 코딩 팀 가이드 (PDF) |

처음이라면 `docs/guide/`의 가이드 PDF 앞쪽 **한 장 요약**부터 읽어 주세요.
