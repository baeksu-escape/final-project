★한 장 요약

꼭 지킬 5가지

  1. CSS·디자인은 AI에게 맡기지 않는다. 프론트 담당자의 영역.
  2. 요청한 부분만 고치게 한다. 다른 파일이 바뀌었으면 되돌린다.
  3. DB·API를 바꿨으면 로그를 남긴다. docs/logs/
  4. 정해지지 않은 건 AI가 정하지 않는다. 선택지를 받아 팀에 가져온다.
  5. 설명할 수 없는 코드는 커밋하지 않는다.

md에 일부러 넣지 않은 것

DB 테이블·컬럼, API 형식, 폴더 구조, 환경 세팅, 학습 데이터 규칙은 팀원이 직접 정할 영역이라 AI 문서에서 뺐습니다. AI 문서에 초안을 적어 두면 AI가 그것을 "정해진 규칙"으로 받아들여 팀이 고민하기 전에 설계가 굳어집니다. 참고용 초안은 8장에 남겨 두었습니다.

"토큰 아끼기"를 md에 넣지 않은 이유

md는 모든 팀원의 AI가 매번 읽습니다. "짧게 답해라", "파일 읽지 마라" 같은 지시를 md에 넣으면 무료 사용자에게는 도움이 될 수 있어도, 자세한 설명이 필요한 순간이나 유료 사용자에게는 오히려 방해가 됩니다. 한도를 아끼는 건 요청하는 방법으로 하는 것이 맞습니다. 그래서 5장에 사람의 습관으로 정리했습니다.

2팀 원칙과 그 이유

AI는 AGENTS.md의 규칙을 지키도록 되어 있지만, 사람이 이유를 알아야 AI가 규칙을 벗어날 때 알아챌 수 있습니다.

① 브랜치를 합칠 때 오류가 나지 않게

6명이 기능별로 각자 브랜치에서 개발합니다. 문제는 여러 기능이 함께 쓰는 파일입니다 — pom.xml, package.json, 공통 설정, 공통 응답 클래스, 라우터, Security 설정, DB 스크립트. AI는 요청하지 않아도 "김에" 이런 파일의 포맷을 정리하거나 이름을 바꾸는 경향이 있어서, 합칠 때 충돌이 납니다.

  • 공유 파일을 고쳐야 하면 Discord #개발에 먼저 알린다.
  • AI가 요청과 상관없는 파일까지 바꿨다면 그 부분은 되돌리고 커밋한다.
  • 명세에 "계산을 공유한다"고 적힌 기능(N-16·N-20, N-17·N-18·N-21, N-21·N-22)은 담당자끼리 함수 하나를 함께 쓰도록 미리 얘기한다.

② 스타일·CSS는 프론트 담당자의 영역

AI는 "더 보기 좋게" 하려고 색·간격·클래스명을 쉽게 바꿉니다. 각자 AI에게 화면을 맡기면 화면마다 디자인이 달라지고, 프론트 담당자가 만든 테마(기본/블랙)가 깨집니다.

  • AI는 CSS·className·인라인 스타일을 요청 없이 고치지 않고, 필요하면 제안만 합니다.
  • Claude Code에서는 CSS 파일을 고치려 하면 확인 창이 뜹니다(.claude/settings.json). 내가 프론트 담당이 아니면 거절하세요.

③ 주석 1~2문장 + N-ID

중간 시연과 최종 발표에서 각자 자기 코드를 설명해야 하고, 팀원끼리 서로의 코드를 읽어야 합니다. AI가 만든 코드는 길고 낯설기 쉬워서, 함수마다 "무엇을 하는지" 한 줄이 있으면 읽는 속도가 크게 달라집니다.

// N-12 나의 신용 리포트 — 기존·대안 점수를 함께 조회한다.

④ DB·API·대량 백엔드 변경은 반드시 로그

DB 컬럼 하나, API 응답 필드 하나가 바뀌면 다른 그룹의 화면과 기능이 바로 깨질 수 있습니다. 그래서 백엔드를 AI가 못 건드리게 막는 대신, 바꿨으면 반드시 기록하고 팀원이 확인하는 방식으로 정했습니다.

로그를 반드시 남기는 경우
DB 관련 변경(테이블·컬럼·DDL) — 1건이라도
API 경로나 요청·응답 필드 추가·변경
한 작업에서 백엔드 파일 3개 이상 변경
빌드·의존성 파일이나 공통 설정 변경

⑤ 모르면 추측하지 않는다

등급 경계, 응답 형식, 타임아웃, 테이블 이름 등 아직 정하지 않은 것(decisions.md의 D-xx)이 많습니다. AI는 모르는 것도 그럴듯하게 지어내므로, 미정 항목은 상수로 빼고 TODO(D-xx)를 달도록 했습니다. AI가 선택지를 물어보면 혼자 고르지 말고 팀에 가져오세요.

미정 사항은 AI의 판단보다 사용자의 의견이 우선

AI가 "이게 더 좋아 보인다"며 미정 사항을 정해 버리면, 팀이 결정했을 때 다시 고쳐야 합니다. 그래서 AGENTS.md와 decisions.md에 "미정 항목은 AI가 스스로 정하지 않고, 선택지를 보여 주고 사용자가 고르게 한다"고 적어 두었습니다. AI가 이 규칙을 어기고 혼자 정했다면 그 부분을 되돌리고 다시 물어보게 하세요.

그 밖의 약속

  • 합성 데이터만 쓰고, 실제 개인정보·API 키는 프롬프트에도 넣지 않는다.
  • 대안 점수가 더 낮은 집단도 숨기지 않는다. 금리·한도는 "참고 정보"로만 보여 준다.
  • AI는 push·병합을 스스로 하지 않는다. 올리는 건 사람이 한다.

3도구별 사용법

도구마다 규칙 파일을 읽는 방식이 다릅니다. 저장소 폴더를 직접 여는 코딩 도구는 규칙을 스스로 읽고, 웹 채팅은 우리가 붙여 넣어야 합니다.

도구규칙을 읽는 방식할 일
Claude Code (VS Code 확장)
Claude Pro 이상		루트 CLAUDE.md 자동 → AGENTS.md 불러옴저장소 루트 폴더를 VS Code로 열고 시작하면 됩니다.
Codex
ChatGPT Plus		루트 AGENTS.md 자동저장소 루트에서 시작합니다.
Gemini 코딩 도구
Gemini CLI · Code Assist		루트 GEMINI.md 자동 → AGENTS.md 불러옴저장소 루트에서 시작합니다. 불러오기가 안 되는 것 같으면 첫 메시지에 "AGENTS.md를 먼저 읽어 줘"라고 적습니다.
웹 채팅
Claude·ChatGPT·Gemini 웹, 무료 포함		저장소를 못 읽음대화 첫 메시지에 docs/ai/PASTE.md의 블록을 붙여 넣고, 고칠 파일 내용을 함께 붙입니다.
Google AI Mode지침을 기억하지 못함코드 작성보다 개념 이해·에러 검색·학습에 씁니다. 코드를 받아 쓸 때는 우리 규칙(CSS·주석)을 직접 확인합니다.

Claude Code를 쓸 때

  • 계획 모드(plan 모드): 파일을 여러 개 고치는 작업은 먼저 계획을 보여 달라고 하세요. 계획을 읽고 "1, 3번만 진행해"처럼 고를 수 있습니다.
  • 확인 창: CSS 수정, git push, rm 등을 하려 하면 확인 창이 뜹니다. 무엇을 왜 하려는지 읽고 허락하세요. 습관적으로 "항상 허용"을 누르지 마세요.
  • 파일 지정: 대화에 파일을 지정(@파일명)하면 AI가 엉뚱한 파일을 찾아 헤매지 않습니다.
  • Claude 앱(웹·데스크톱)은 문서 정리·설계 상의에, VS Code 확장은 실제 코드 작업에 나눠 쓰면 편합니다.

웹 채팅을 쓸 때

  1. 새 대화 → PASTE.md 블록 붙여 넣기
  2. 해당 기능의 features.md 내용(그 N-ID 부분만) 붙여 넣기
  3. 고칠 파일의 관련 부분만 붙여 넣고 요청 (4장 템플릿)
  4. 받은 코드를 내 파일에 옮긴 뒤, CSS·주석 규칙을 지켰는지 직접 확인
웹 채팅에서 자주 생기는 문제

웹 채팅은 우리 저장소의 다른 파일을 모르기 때문에 이미 있는 함수와 같은 일을 하는 함수를 새로 만들거나, 다른 이름을 지어 오는 경우가 많습니다. 붙여 넣기 전에 "이미 비슷한 게 있는지"를 확인하세요.

심화: 스킬(Skills) — 익숙해진 뒤에

Claude Code에는 .claude/skills/이름/SKILL.md에 "특정 작업용 매뉴얼"을 넣어 두는 기능이 있습니다. 평소엔 이름만 알고 있다가 관련 작업에서 꺼내 읽습니다. 지금은 팀 설계가 정해지지 않아 넣지 않았습니다. 나중에 그룹별로 API 형식이나 모델 서버 구조가 확정되면, 그 그룹이 직접 자기 기능의 스킬을 만들어 보는 것을 권합니다. 꼭 지켜야 하는 규칙은 스킬이 아니라 AGENTS.md에 둡니다.

AI의 결과물이 나쁜 이유의 대부분은 요청이 모호해서입니다. 아래 네 가지만 적어도 결과가 확연히 달라지고, 다시 시키는 횟수가 줄어 한도도 아낄 수 있습니다.

더 잘 쓰는 요령

  • 계획 먼저: 큰 작업은 "바로 코드 짜지 말고 단계별 계획부터 보여 줘"로 시작합니다. 계획에서 틀린 걸 고치는 게 코드에서 고치는 것보다 훨씬 쌉니다.
  • 작게 자르기: "N-16 전체"보다 "N-16 비율 계산 함수 → 그다음 API → 그다음 화면 연결" 순서로.
  • 설명 요청: 받은 코드에서 모르는 부분은 "이 부분이 왜 필요한지 두 줄로 설명해 줘". 발표 준비가 따로 필요 없어집니다.
  • 반대 의견 허락: "더 단순한 방법이 있으면 말해 줘"를 붙이면 과하게 복잡한 코드가 줄어듭니다.
  • 테스트로 목표 정하기: "버그 고쳐 줘" 대신 "이 버그를 재현하는 테스트를 먼저 쓰고, 통과하게 고쳐 줘".

5토큰·한도 아끼는 습관

무료 등급은 하루·시간당 한도가 빨리 찹니다. 한도는 대화 길이와 붙여 넣는 양에 가장 크게 좌우됩니다.

습관이유와 방법
한 대화 = 한 작업AI는 매번 대화 전체를 다시 읽습니다. 대화가 길수록 한 번의 질문이 비싸지고, 앞의 내용을 헷갈리기 시작합니다.
길어지면 요약해서 새 대화"지금까지 결정한 것과 남은 일을 5줄로 요약해 줘" → 새 대화에 그 요약을 붙여 시작.
필요한 부분만 붙이기파일 전체 대신 관련 함수만, 에러 로그 전체 대신 Caused by 주변 몇 줄만. CSV·모델 파일은 붙이지 않고 컬럼 목록 정도만.
출력 형태 지정"바뀐 부분만 보여 줘", "설명은 3줄 이내" 처럼 그때그때 정합니다(md에 고정하지 않는 이유는 1장).
같은 걸 다시 시키지 않기마음에 안 들면 처음부터 다시 시키기보다 "2번 함수에서 예외 처리만 바꿔 줘"처럼 고칠 곳을 짚습니다.
도구를 나눠 쓰기개념 이해·검색은 Google AI Mode나 무료 채팅, 실제 코드 수정은 저장소를 읽는 도구. 설계처럼 어려운 질문에 좋은 모델을 아껴 씁니다.
같은 실수를 반복하면 끊기AI가 같은 오류를 두세 번 반복하면 대화를 이어 가지 말고, 요약과 함께 새 대화를 엽니다.
한도를 가장 많이 아끼는 방법

4장의 템플릿대로 처음부터 범위를 정해 주는 것입니다. "다시 해 줘"가 줄어드는 만큼 한도가 남습니다.

6매일 쓰는 체크리스트와 숙련 단계

작업 시작 전

  • 최신 develop을 받았다 (git pull origin develop)
  • 오늘 할 기능의 N-ID와 features.md 내용을 확인했다
  • docs/logs/에서 최근 로그를 훑어봤다 (내가 쓸 파일을 누가 바꿨는지)
  • 관련된 미정 항목(D-xx)이 있는지 decisions.md를 봤다

AI에게 맡길 때

  • 요청에 N-ID · 범위 · 하지 말 것 · 확인 방법을 적었다
  • 여러 파일이 바뀌는 작업은 계획부터 받았다
  • AI가 물어본 미정 사항을 혼자 정하지 않고 팀에 가져갔다

끝나고 커밋 전

  • 바뀐 파일 목록(diff)을 직접 확인했다 — 요청 밖 파일, CSS 변경이 없다
  • 실제로 실행해 봤다 (빌드·화면·Swagger)
  • 새 함수·API에 1~2문장 주석과 N-ID가 있다
  • 이 코드를 팀원에게 내 말로 설명할 수 있다
  • DB·API·백엔드 3개 이상·공통 설정을 바꿨다면 로그를 썼다

숙련 단계 — 하루하루 올라가기

1단계 · 따라 하기
  • 템플릿을 그대로 복사해서 요청
  • 함수 하나 단위로 작게 맡기기
  • 받은 코드를 한 줄씩 설명 요청
2단계 · 범위 다루기
  • 계획 먼저 받고 골라서 진행
  • 대화가 길어지면 요약 후 새 대화
  • diff 확인이 습관이 됨
3단계 · 팀과 맞추기
  • 로그 작성·남의 로그 검수
  • 공유 파일 변경 전 공지
  • AI의 선택지를 팀 결정으로 연결
4단계 · 도구 다루기
  • 도구를 목적별로 나눠 쓰기
  • 테스트로 목표를 정하고 맡기기
  • (선택) 그룹별 스킬 만들어 보기

7Git · PR · 작업 로그 흐름

하루 작업 흐름

1. git checkout develop && git pull origin develop
2. git checkout -b feature/FP-12-credit-report     (Jira 이슈가 없으면 feature/기능명)
3. AI와 작업 → diff 확인 → 실행 확인
4. git commit -m "feat - N-12 신용 리포트 조회 API 추가"
5. (PR 직전) 최신 develop 다시 반영 → 다시 실행 확인
6. 해당되면 docs/logs/에 로그 파일 추가
7. git push → GitHub에서 PR 생성 → 검토 후 병합
구분규칙
브랜치feature/…, fix/…를 develop에서 만든다 → PR → develop → main. main·develop에 직접 push 금지.
커밋 메시지행위 - 내용, 관련 N-ID 포함. 행위: feat, fix, docs, style, refactor, test, chore. (형식 재논의 여지: D-17)
충돌다른 사람의 코드를 지우는 쪽으로 해결하지 않는다. AI에게 "충돌 부분과 선택지를 보여 줘"라고 하고, 필요하면 해당 담당자와 같이 본다.
비밀값.env, application-local.yml은 올리지 않는다. 실수로 올렸다면 바로 Discord에 알리고 키를 다시 발급한다.

작업 로그와 검수

  • 작업 하나에 파일 하나: docs/logs/YYYY-MM-DD_작성자_요약.md — 한 파일에 이어 쓰면 합칠 때 충돌이 납니다.
  • 양식은 _TEMPLATE.md를 복사합니다. AI에게 "이번 작업 로그를 템플릿대로 써 줘"라고 하면 초안을 만들어 줍니다. 단, "확인함"에는 실제로 해 본 것만 남기세요.
  • 검수 담당과 PR 병합 절차는 docs/logs/README.md에 정리되어 있습니다. 다른 사람의 로그를 읽다가 문제가 보이면 Discord #개발에 알려 주세요.
  • AI는 검수 칸에 대신 서명하지 않습니다. 검수는 사람이 합니다.

AI · 바이브 코딩

바이브 코딩코드를 직접 다 쓰는 대신 AI에게 말로 요청해서 코드를 만들고, 사람은 확인·수정하는 개발 방식.
프롬프트AI에게 보내는 요청 문장. 4장의 템플릿이 좋은 프롬프트의 틀.
토큰 (AI)AI가 글을 처리하는 단위. 대화가 길고 붙여 넣는 양이 많을수록 많이 쓰고, 무료 한도가 빨리 찬다. 로그인용 "토큰(JWT)"과는 다른 말.
컨텍스트AI가 한 대화에서 기억하고 있는 내용 전체. 너무 길어지면 앞 내용을 헷갈린다 → 새 대화로.
md (마크다운)#, - 같은 기호로 제목·목록을 표시하는 텍스트 파일 형식. 확장자 .md.
AGENTS.md / CLAUDE.md / GEMINI.md코딩 도구가 대화를 시작할 때 자동으로 읽는 규칙 파일. 원본은 AGENTS.md.
Claude CodeClaude가 내 프로젝트 폴더의 파일을 직접 읽고 고치는 코딩 도구. VS Code 확장으로 쓸 수 있다.
plan 모드 (계획 모드)AI가 코드를 바로 고치지 않고 계획만 먼저 보여 주는 모드. 여러 파일을 바꾸는 작업 전에 쓴다.
확인 창 (권한 요청)AI가 CSS 수정·git push 같은 작업을 하기 전에 허락을 묻는 창. 이유를 읽고 누른다.
스킬Claude Code에서 특정 작업용 매뉴얼을 넣어 두는 기능. 지금은 쓰지 않는다 (3장).
웹 채팅브라우저·앱에서 쓰는 Claude·ChatGPT·Gemini 대화창. 저장소 파일을 못 읽어서 PASTE.md를 붙여 넣는다.

Git · 협업

저장소 (repo)프로젝트 코드 전체와 변경 기록이 들어 있는 곳. 우리는 GitHub를 쓴다.
브랜치각자 작업하는 갈래. main(발표용 안정본) · develop(합치는 곳) · feature/…(개인 작업).
커밋 (commit)변경 내용을 한 단위로 저장하는 것. 메시지 형식 행위 - 내용.
pull / pushpull: 서버의 최신 코드를 받아 오기. push: 내 커밋을 서버에 올리기.
PR (Pull Request)"내 브랜치를 develop에 합쳐 주세요"라는 요청. 검토를 거쳐 병합된다.
병합 (merge)두 브랜치의 변경을 하나로 합치는 것.
충돌 (conflict)두 사람이 같은 곳을 다르게 바꿔서 자동으로 합칠 수 없는 상태. 남의 코드를 지우지 말고 같이 본다.
diff무엇이 바뀌었는지 보여 주는 비교 화면. 커밋 전에 꼭 본다.
Jira (FP)팀 작업(이슈) 관리 도구. 브랜치 이름에 FP-12 같은 이슈 키를 넣으면 연결된다.

개발

프론트엔드 / 백엔드프론트: 사용자가 보는 화면(React). 백엔드: 로그인·DB·계산을 처리하는 서버(Spring Boot).
모델 서버신용점수와 SHAP을 계산하는 별도 서버(FastAPI). 백엔드만 호출한다.
API / 엔드포인트API: 서버끼리 주고받는 약속. 엔드포인트: 그 약속의 주소(예: /api/v1/...).
요청 · 응답 필드API로 보내고 받는 데이터의 항목 이름. 바꾸면 다른 기능이 깨질 수 있어 로그 대상.
DTOAPI로 주고받는 데이터를 담는 Java 클래스.
DB · 테이블 · 컬럼데이터 저장소(Oracle) · 엑셀의 시트 같은 표 · 표의 열.
DDL테이블을 만들거나 바꾸는 SQL 문(CREATE TABLE 등).
스키마데이터의 구조(어떤 항목이 어떤 형식으로 들어가는지)를 정의한 것.
mock (목)상대 서버가 아직 없을 때 쓰는 가짜 응답. 실제 응답과 같은 모양으로 만든다.
JWT (토큰 인증)로그인하면 서버가 발급하는 출입증. 요청마다 함께 보내 본인임을 증명한다.
SHAP모델 점수에 각 항목이 얼마나 영향을 줬는지 보여 주는 방법. 원인(인과)을 증명하지는 않는다.
합성 데이터실제 사람 정보가 아니라 규칙에 따라 만들어 낸 가짜 데이터.
마스킹개인정보 일부를 가리는 것(예: 010-****-1234).
하드코딩 / 상수·설정값하드코딩: 값을 코드 곳곳에 직접 박아 넣는 것. 상수·설정값: 한곳에 모아 이름을 붙여 두는 것 → 바꾸기 쉽다.
의존성 / 라이브러리프로젝트가 가져다 쓰는 외부 코드. pom.xml·package.json에 적힌다.
환경 변수 / .env비밀번호·API 키처럼 코드에 직접 쓰면 안 되는 값을 따로 두는 곳. 절대 올리지 않는다.
Swagger백엔드 API를 브라우저에서 직접 호출해 볼 수 있는 화면.
리팩터링동작은 그대로 두고 코드 구조만 다듬는 것. 요청 없이 시키지 않는다.
