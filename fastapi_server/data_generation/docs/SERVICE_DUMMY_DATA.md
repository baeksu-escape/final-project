# 서비스 더미 데이터

서비스 화면·DB·연동 개발에 쓰는 더미 데이터 세 가지를 만든다(v3.5.0부터 외부 API에 간편결제·공공보험 응답, v3.5.7부터 신용평가사·공과금 응답 추가). 필드 정의는 `DATA_DICTIONARY.csv`의 `dataset=service_dummy` 행을 따른다.

| 데이터 | 생성 스크립트 | 출력 |
|---|---|---|
| 더미 대출상품 | `build_loan_products.py` | `service_dummy/loan_products.csv` |
| 가입 회원 더미 | `build_members.py` | `service_dummy/members/` |
| 외부 금융·통신·간편결제·공공보험·신용평가사·공과금 API 더미 응답 | `build_external_api.py` | `service_dummy/external_api/` |

기준점과 가정 값은 `reference/service_dummy_anchors.json`에, 대출 종류 매핑은 `reference/loan_type_mapping.json`에 둔다. 각 값에 근거를 적고 고정 예제로 검사한다.

## 학습 데이터와의 분리

- `service_dummy/`는 학습용 `data/`, `thinfile/`과 다른 폴더다. 회원 데이터는 모델 학습에 쓰지 않는다.
- 회원 원천은 씬파일 생성기를 **회원 전용 시드(20261101)**로 임시 폴더에서 실행해 만든다. 학습용 시드(20261030, 20261029)와 같으면 생성을 멈춘다. 같은 생성 규칙이라 분포는 학습 데이터와 비슷하지만 같은 사람의 복사본은 아니다.
- 임시 폴더의 라벨·집단 설계값(`cohort`, 라벨, 노출 확률)은 저장하지 않는다. 회원 데이터에는 서비스가 실제로 알 수 있는 값만 남긴다.

## 더미 대출상품

- 업권별 금리 기준점(연 %): 은행 일반신용대출 6.33, 저축은행 10.23, 신협 5.28(2026년 8월 한국은행 가중평균금리). 카드론 14.66은 업계 평균이 아니라 2026년 7월 카드사 한 곳(롯데카드)의 카드론 평균금리다. 같은 보도의 신용점수 700점 이하 8개사 평균은 17.45%다. 업계 전체 평균을 확보하면 바꾼다. 캐피탈 13.0은 공식 평균을 찾지 못한 가정값이다.
- 저축은행·신협 값은 신용대출만의 평균이 아니라 업권 전체 대출 평균이다. 상품 금리 범위는 기준점 주변의 가정 스프레드로 만든다.
- 모든 상품의 금리 범위는 `최저 ≤ 기준점 ≤ 최고 ≤ 20%`를 지킨다(법정 최고금리). 최종 생성 전에 최고금리 변경 여부를 다시 확인한다.
- 한도, 기간, 대상 직군, 연소득 대비 한도 배수는 가정이다. 기관명은 `가상은행 A`처럼 가상 이름만 쓰고 실제 기관명·상품명을 쓰지 않는다.

## 가입 회원 더미

- `members.csv`: 회원 ID(`MEM`+6자리), 예약 도메인 `example.com` 이메일, 닉네임, 나이, 출생연도, 직군, 가입일(2026-01-01~2026-09-18), 시연 시작 외부 조회 동의 상태 `external_data_consent`(가정 80%). 요청 시 동의 확인은 목 서버가 수행한다.
- `member_monthly_inputs.csv`: 회원이 입력한 월별 소득·생활지출·상환액과 **입력일**. v3.5.11부터 **최근 완결 12개월(2025-09~2026-08)**을 입력한다(N-22 비수기 판별에 12개월 소득이 필요하다는 서비스 결정, `reference/service_dummy_anchors.json`의 `members.input_months`). v3.5.7~v3.5.10은 가입 장벽을 줄이려고 6개월(2026-03~2026-08)만 입력했다. 12개월을 다 입력하지 않은 회원은 서비스 대상이 아니라서 더미에 넣지 않았다. 입력일은 월말 1~10일 뒤이고, 가입 전 달은 가입일에 한꺼번에 입력한 것으로 둔다. 입력일 난수는 원천 12개월 전체에 대해 뽑으므로 2026-03~2026-08 행의 값과 입력일은 v3.5.7~v3.5.10과 같다. 학습 모델 표의 기본 입력 집계도 12개월(`members.model_feature_months`)이다(v3.5.13). 6개월은 보존·참고용(`members.model_feature_months_6m`, `compatibility_only`)이며 기본 학습에서 제외한다(`DATA_SPEC.md`). 소득은 월별 값으로만 있다.
- 비밀번호는 넣지 않는다. 이메일·닉네임은 평문 더미이므로 서비스 DB에 넣을 때는 서비스의 암호화 정책을 적용한다.
- `ledgers/`: 외부 API 응답의 근거 원장(대출·카드·카드 이용·통신 미납 월, v3.5.0부터 `digital_payment_monthly.csv`·`social_insurance_monthly.csv`). 서비스 전달 대상이 아니라 API 더미의 정합성 확인용이다.
- 간편결제·사회보험 원장은 학습 데이터와 같은 규칙(`NONFINANCIAL_SOURCES.md`)을 회원 시드(20261101, 오프셋 2)로 실행해 만든다. 위험 기울기 같은 설계값은 저장하지 않는다.

## 대출 종류·금리 방식 (N-05-3)

- 회원 원장과 금융 응답의 대출 목록에 `loan_type_code`와 `rate_type`을 추가한다. 종류 매핑은 시연 가정이다(`basis=assumption`). kind 0은 CREDIT, 그중 카드 업권(sector 1)은 CARD_LOAN, 1·7은 MORTGAGE, 2·3·4·5·6·8은 OTHER다. JEONSE와 BUSINESS_OPERATING은 대응 원천 코드가 없어 생성되지 않는다.
- 금리 방식은 회원 계좌 ID의 SHA-256 앞 8자리 정수의 홀짝으로 정한다. 짝수 FIXED, 홀수 VARIABLE이며 학습 데이터와 같은 함수를 사용한다(학습 출력은 소문자). 난수는 사용하지 않는다.

## 외부 금융·통신 API 더미 응답

- 회원당 금융 1건, 통신 1건의 JSON 응답을 JSON Lines로 저장한다. 기관 데이터는 시작 동의 상태와 무관하게 전 회원 몫을 생성하며 응답은 전원 `status=OK`다.
- 금융 응답: 대출 목록, 카드 목록, 카드 30일 구간 이용액. 회원 원장에서 만들므로 대출 잔액 합이 회원 부채와 같고, 월 상환액도 회원 입력과 같은 원장에서 나온다.
- 통신 응답: 청구월별 청구액·납부기한·납부일·납부 상태. 연체 여부는 회원 월별 원천의 `telecom_late`와 같다. 기준일까지 갚지 않은 연체 청구는 `paid_date`가 null이다.
- 청구액은 개인마다 다르다. 회원별 기본 요금을 로그정규분포(중앙값 55,000원, sigma 0.35)에서 뽑고(약 90%가 31,000~98,000원), 매월 ±5% 수준의 잡음을 더한 뒤 15,000~200,000원으로 자른다. 중앙값과 sigma는 가정이며 소득·직군과는 연결하지 않았다. 근거는 가구당 통신서비스비 월 10만 원(통계청 가계동향 2023년)과 이동통신 가입자당 매출 2.5~3만 원(2023년 말) 사이의 값이다.
- 간편결제 응답(v3.5.0, `payment_responses.jsonl`): `provider=dummy_payment_api`, `provider_scope=npay_synthetic`, 12개월 `months[]`(월, 관측 상태, 결제 건수·금액·결제일 수). 회원 원장과 월 수·금액 합이 같다.
- 공공보험 응답(v3.5.0, `public_insurance_responses.jsonl`): `provider=dummy_public_insurance_api`, 국민연금·건강보험 각 12개월 `records[]`(가입 상태, 가입유형, 고지액, 본인 부담, 납부액, 기한, 납부일, 납부 상태). 아무것도 내지 않은 달은 `paid_date`가 null이다.
- 신용평가사 응답(v3.5.7, `credit_bureau_responses.jsonl`): `provider=dummy_credit_bureau_api`, `credit_info` 객체에 회원의 207열 신용정보와 신용이력 열 4개(`credit_history_days`, `credit_card_observed_months`, `cb_available`, `credit_usage_available`). 열 이름·뜻은 학습 데이터의 `base_207`과 같다. 미관측 값은 씬파일 `model_inputs.csv` 규칙대로 null이다(`CB=5` 자리표시자는 null). 라벨 원천 `결과값(연체회차)`와 금융사 제시 한도·금리 `PRE_LMT`·`PRE_RT`는 넣지 않는다. 회원 생성 때 버리던 씬파일 생성기의 207열을 원장(`ledgers/credit_bureau.csv`)으로 남겨 만든다.
- `CB`는 **1 우량~10 고위험**의 교육용 등급이며 공식 신용점수가 아니다. 서비스가 회원에게 보여 줄 등급(아래)과 별개다.
- 공과금 응답(v3.5.7, `utility_responses.jsonl`): `provider=dummy_utility_api`, 통신 응답과 같은 `bills[]` 형식(청구월, 청구액, 기한, 납부일, 상태). 미납 여부는 회원 월별 원천의 `utility_late`와 같다. 청구액은 회원별 기본 요금 로그정규(중앙값 60,000원, sigma 0.4)에 월 잡음(sigma 0.15)을 곱하고 10,000~300,000원으로 자른 값이며 모두 가정이다(1인 가구 전기·가스·수도 합산 개인 통계를 확인하지 못했다). 납부기한은 청구월 20일(가정). 공과금 금액은 별도 난수 흐름을 써서 기존 네 응답은 v3.5.6과 바이트 단위로 같다.
- 외부 조회 동의 하나로 여섯 응답을 함께 다루되, 동의 확인은 목 서버가 요청 시 수행한다. `external_data_consent`는 시연 시작 상태이며 저장된 기관 응답의 OK 여부와 분리한다. 종전 `CONSENT_REQUIRED`·빈 목록(신용평가사는 빈 객체)은 DB 생성기가 지원하는 호환 입력 형식일 뿐 현재 생성 정책이 아니다.
- 응답 형식은 연동 개발용 예시이며 실제 기관 API 규격을 따른 것이 아니다.

## 서비스 등급과 상태 코드 (v3.5.7, v3.5.12 수정)

회원 등급은 학습 데이터의 `CB`가 아니라 **모델 점수**를 구간으로 나눠 정한다. 점수 산식은 모델 팀이 정하고, 이 패키지는 이름과 코드만 정한다. 결과는 서비스 DB(v0.3.2)에서는 `ASSESSMENT`(틀만 있음, 시드 없음)에 넣는다. 옛 더미 DB(`dummy_db/`, v2.x)에서는 같은 역할의 표가 `MEMBER_CREDIT_GRADE`였다.

| 상태 `GRADE_STATUS_CODE` | 뜻 | 화면 예시 | 등급 `GRADE_BAND_CODE` |
|---|---|---|---|
| `SCORED` | 점수 산정됨 | – | `GOOD` / `STANDARD` / `CAUTION` |
| `NOT_SCORABLE` | 점수 계산에 필요한 정보가 없음 | 산정 불가 | 없음 |

- 회원 월 입력 12개월은 필수다. 덜 차면 점수 산출 요청 자체를 막으므로 입력 부족 상태는 두지 않는다(v3.5.12, 이전 `INSUFFICIENT_INPUT`).
- 서비스 점수는 0~1000, 등급 경계는 665·780(Caution 0~664 / Standard 665~779 / Good 780~1000)이다. 시연용 임시값이며 모형 학습 후 다시 정한다(D-01). 값은 DB 생성기 `build_db.py` 상수 한 곳에 있다.
- 코드 값은 영어 대문자로 데이터에 넣고, 화면 문구(산정 불가, 등급의 한글 이름)는 데이터에 넣지 않는다. 이름이 바뀌어도 데이터를 다시 만들 필요가 없다.
- 학습 데이터에는 `NOT_SCORABLE`에 해당하는 사람이 없다. 씬파일의 `eval_future_credit_exposure = 0`은 학습 대상 표시이며 산정 불가와 다르다.
- 이전에 임시로 논의한 "`CB` 1~3 / 4~7 / 8~10을 3단계로 나누는 안"은 쓰지 않는다. 회원에게 `CB`가 없던 상태에서 나온 안이고, 등급은 모델 점수에서 나오기 때문이다.

## 실행 순서

```bash
python -m generate.build_loan_products
python -m generate.build_members        # 내부에서 씬파일 생성기를 회원 시드로 실행
python -m generate.build_external_api   # build_members 출력 필요
```

각 스크립트는 저장 전에 `service_dummy_logic.py`의 검사 함수를 실행하고, 규칙 위반이면 파일을 쓰지 않고 멈춘다.

## 검사하는 규칙

| 대상 | 규칙 |
|---|---|
| 대출상품 | ID 고유, 0 < 최저 ≤ 기준점 ≤ 최고 ≤ 20%, 최소 한도 ≤ 최대 한도, 기간 범위, 직군·업권 코드, 가상 기관명, `is_dummy=1` |
| 회원 | 회원 시드 ≠ 학습 시드, ID·이메일 고유, `example.com`, 가입일 ≤ 기준일, 입력일 > 월말·입력일 ≥ 가입일·입력일 ≤ 기준일, 회원-월 중복 없음, 음수 금액 없음 |
| 외부 API | 회원마다 응답 정확히 1건(누락·중복·모르는 회원 ID 모두 오류), 시작 동의와 무관하게 전원 OK, 대출 잔액 합 = 원장, 개설일 ≤ 기준일, 통신 연체 상태 = 원천, 납부일 규칙, 기한·납부일 ≤ 기준일. 요청 시 동의 확인은 목 서버 담당 |
| 월 입력 기간(v3.5.7, v3.5.11부터 12개월) | 회원마다 `members.input_months`의 12개월을 정확히 입력 |
| 신용평가사·공과금 응답(v3.5.7) | 회원마다 1건·전원 OK, 시작 동의 상태와 분리. 원장에 라벨 원천·제시 한도·금리 열 없음, 응답 값 = 원장(null 위치 포함), `CB` 1~10, `CB` null ⇔ `cb_available = 0`, 공과금 미납 상태 = 원천, 납부일 규칙 |
| 간편결제·공공보험 원장·응답(v3.5.0) | 원장: `nonfinancial_sources.check_payment`·`check_insurance` 규칙(`NONFINANCIAL_SOURCES.md`). 응답: 회원마다 1건·전원 OK, 시작 동의 상태와 분리, 결제 월 수·금액 합 = 원장, 보험 행 수·납부액 합 = 원장, 납부일 유무 = 납부 상태 |

## 서비스 DB 시드(v0.3.2)와 백엔드 개인정보 규격 (N-02-4, N-05)

DB 생성기는 `docs/spec/sql/dummy_db/tools/build_db.py`, 기준 DDL은 `docs/spec/sql/avenue_ddl.sql`의 v0.3.2(51개 표)다. 별도 Oracle 개발 스키마 적재를 권장한다. 시연 계정은 직군별 사용자 3명(`demo_employee`·`demo_self`·`demo_free`)과 관리자 `demo_admin`(N-01-5)이다.

- v0.3.2의 `USER_LOAN.CONSENT_ID`는 불러온 대출이면 필수, 직접 입력이면 NULL이다. 통신비·공과금·간편결제·사회보험·신용 프로필에도 같은 출처·동의 ID 규칙이 있다. 동의는 최대 1년이며 만료·철회·탈퇴 시 해당 동의로 불러온 행을 삭제한다. 기존 시드는 새 DDL에 맞춰 사용자가 다시 생성한다. 이 변경은 학습 데이터 자체를 바꾸지 않는다.

- `generate.build_members`는 기존 회원·12개월 입력·원장 값을 유지하고 **`members/member_asset_snapshots_v02.csv`**만 추가한다(`member_id`, `base_month`, `total_asset_amt`). 기존 합성 프로필의 자산 원 단위 값을 그대로 옮기며 새 난수를 소비하지 않는다.
- v0.2 소득 시드는 급여소득자 `SALARY` 1행, 자영업·프리랜서 `MONTHLY_INCOME` 12행이다. 기준월은 임시 **2026-08(TODO(D-16))**이며 지출·대출·자산은 한 세트다. 지출은 회원당 `FIXED` 1행 = 원천 12개월 평균 월 지출(원 단위 ROUND_HALF_UP). 평가 시드는 비운다.
- 대출 종류·금리 방식은 원장 `members/ledgers/loans.csv`의 `loan_type_code`·`rate_type`에서 읽는다(기관 응답 `loanTypeCode`와 같은 원천 값). 두 필드가 없는 옛 원천은 `OTHER`·`UNKNOWN`으로 처리한다. 종류 매핑은 가정이며 대출 입력 항목은 미확정이다(TODO(D-27)).
- 기관 데이터는 동의와 무관하게 전 회원 몫을 생성하고 응답은 전원 `status=OK`다. 동의는 목 서버가 요청 시 확인하며 `members.csv.external_data_consent`는 시연 시작 동의 상태다. v0.2 시드의 USER_CONSENT와 대안 데이터 IMPORTED 행은 이 시작 상태로 제한한다. DB 생성기는 종전 동의 제한 응답도 호환 입력으로 지원하며 응답 status를 동의로 해석하지 않는다.
- 전 회원의 대출 원장은 보존한다. 시작 동의 회원은 `USER_LOAN.SOURCE_CODE=IMPORTED`, 미동의 회원은 `MANUAL`이며 회원별 월 상환 합계가 원천 기준월 상환액과 같아야 한다. v0.3.2에서는 불러온 대출에 동의 ID를 연결한다. 상품별 최소점수·점수대 참고 범위의 시연 가정은 `docs/spec/sql/dummy_db/README.md`를 따른다.
- **공과금 표:** 공과금 응답은 통신비와 같은 `map_bill_rows()`로 `USER_UTILITY_PAYMENT`에 넣고, 동의는 `PROVIDER_CODE=utility`, `ITEM_CODE=UTILITY_BILL`이다. 시작 동의 회원만 IMPORTED 행이다.
- **납부 상태(v0.3.1 U3):** DB에는 `ON_TIME`(납부일 ≤ 기한), `LATE`(납부일 > 기한), `UNPAID`(납부일 NULL)로 저장한다. 기관 응답의 `late` + `paid_date=null`은 `UNPAID`로 바꾼다. 응답 파일 자체는 바꾸지 않는다. 미납 개월 수(`telecom_late`·`utility_late`)는 LATE + UNPAID와 같다(U2).

**백엔드와 맞출 암호화 규격:** 이름·휴대폰·이메일은 UTF-8 → **AES-256-GCM**으로 암호화한다. 값마다 독립적인 **12바이트 난수 IV**, AAD 없음. DB 문자열은 키 버전 접두어 **`v1:` + 표준 Base64(IV 12바이트 + 암호문 + 인증 태그 16바이트)**다(DDL v0.3.1 E2). 복호화 시 첫 `:` 앞 버전으로 키를 고르고(모르는 버전이면 오류), Base64를 푼 뒤 앞 12바이트를 IV로 분리하고 나머지 암호문+태그를 인증 복호화한다. 실제 암호문 길이를 DDL 열 길이와 대조한다.

검색용 값은 **별도 키의 HMAC-SHA256**, UTF-8, **64자 소문자 16진수**다. 이메일은 trim+소문자, 휴대폰은 ASCII 숫자만 남긴 뒤 HMAC을 계산한다. HMAC 열에는 접두어를 붙이지 않는다. 저장 암호문의 원문 자체는 이 검색 정규화와 구분한다.

키는 **`AVENUE_DEV_AES_KEY`**, **`AVENUE_DEV_HMAC_KEY`**의 Base64 값으로 받는다. 환경변수 또는 `--env-file`로 지정한 저장소 밖 env 파일에서 읽고, 시연 계정 비밀번호 `AVENUE_DEMO_PASSWORD`도 같은 곳에서 읽는다. AES는 디코딩 후 정확히 32바이트, HMAC은 최소 32바이트의 별도 키이며 두 키가 같으면 거부한다. 키가 없으면 파일 쓰기 전에 오류로 중단한다. 키·키 지문·원문을 저장소·생성 SQL·로그에 남기지 않는다. 저장소의 `.env`·application 설정 파일은 읽지 않는다. 커밋용 시드는 팀 개발 키 한 쌍(디스코드 비공개 채널로 공유)으로 만들어 커밋한다(절차는 `docs/spec/sql/dummy_db/README.md`). 테스트의 공개 고정 키·비밀번호는 실제 값이 아니다. 의존성은 이 패키지의 `requirements.txt`에 있는 `cryptography==50.0.2`, `bcrypt==5.0.0`이다.
