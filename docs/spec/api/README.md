# API 문서

React → Spring(`/api/**`) → FastAPI(`/v1/**`) 사이의 API를 적는 문서 모음이다. 2026-11-18에 공유 링크로만 보던 정의서·B팀 명세서를 이 폴더로 옮겼다. **이제 이 폴더의 파일이 원본이다.**

## 0. 팀 구성 (A·B·C팀이 누구인가)

이 폴더와 코드 주석에서 쓰는 "A팀·B팀·C팀"(또는 A조·B조·C조)은 아래 팀이다. 기준은 Jira 에픽 FP-73·FP-105·FP-149 이름이다.

| 팀 | 사람 | 맡은 영역 | 주로 맡은 API ID | 명세서 | 브랜치 이름 | Jira 에픽 |
|---|---|---|---|---|---|---|
| A팀 | 우찬, 경환 | 데이터·화면: 회원·인증, 마이페이지, 데이터 입력, 결과 화면, 관리자 계정·로그 | AUTH, MEM(06 제외), INP, ADM-05~10, ADM-ME | [api_spec_a.md](api_spec_a.md) | `feature-A/…` | FP-73 |
| B팀 | 재욱, 범영 | 모델·서버: 모델 학습, DB·DDL, 점수 산출·리포트, 예측 서버(FastAPI) | RPT-01~03, MEM-06, ML-01~04 | [api_spec_b.md](api_spec_b.md) | `feature-B/…` | FP-105 |
| C팀 | 광희, 동주 | 공공통계·활용: 재무 진단, 시뮬레이터, 커뮤니티·신고, 금융사전·AI, 모형 성능 비교 | DIAG, SIM, COMM, HELP, RPT-04, ADM-01·02·11~14 | [api_spec_c.md](api_spec_c.md) | `feature-C/…` | FP-149 |

- API 하나하나의 담당자는 [정의서](api_definition.md) 2장 표의 "담당" 칸이 기준이다. 위 표와 다르면 정의서를 따른다(예: RPT-04 AI 요약은 경로가 RPT지만 광희 담당).
- 담당이 아직 정해지지 않은 API(LOAN, RPT-05, ADM-03 등)는 정의서 4장 "담당 팀이 정해야 할 것"에 있다.

## 1. 문서 지도

| 파일 | 무엇 | 비유 | 관리 |
|---|---|---|---|
| [api_definition.md](api_definition.md) | **API 정의서.** 서비스 전체 API 목록(ID·경로·기능 N-ID·담당·상태), 공통 규칙, 오류 code 목록 | 책의 목차 | 2장 API 행은 만든 사람, 1장·틀은 범영(검수) 🆕 11/20 |
| [api_spec_a.md](api_spec_a.md) | A팀 API 요청·응답 상세 (회원·인증, 마이페이지, 데이터 입력, 관리자) | 본문 | A팀 |
| [api_spec_b.md](api_spec_b.md) | B팀 API 요청·응답 상세 (점수 산출·리포트 RPT, 진단 내역 MEM-06, Spring → FastAPI 내부 ML-01~04) | 본문 | 범영 |
| [api_spec_c.md](api_spec_c.md) | C팀 API 요청·응답 상세 (재무 진단 DIAG, 시뮬레이터 SIM, 커뮤니티 COMM 등) | 본문 | C팀(광희·동주) |

- API ID(AUTH-01, RPT-01, DIAG-07 …)는 정의서가 정한다. 명세서와 코드 주석은 이 ID로 부른다.
- 다른 문서에서 장을 부를 때는 파일 이름을 같이 쓴다. 예: "B팀 명세서(`api_spec_b.md`) 4-4". 정의서·명세서·피처 정의서 모두 "3-2" 같은 번호가 있어 헷갈린다.
- B팀 명세서는 장 번호를 바꾸지 않는다. 코드 주석이 "B팀 명세서 4-3"처럼 번호로 가리킨다.

## 2. 고치는 방법

| 바꾸는 것 | 누가 | 어떻게 |
|---|---|---|
| 내 팀 API의 요청·응답 | 그 API를 만든 사람 | 기능 PR에서 자기 팀 명세서(`api_spec_a/b/c.md`)를 같이 고친다 |
| API 추가·경로 변경·담당·상태 🆕 11/20 | **그 API를 만들거나 바꾼 사람** | 같은 기능 PR에서 정의서 2장의 해당 행을 직접 고친다(경로·기능·주요 표·담당·상태, 바꾼 칸에 `🆕 MM/DD`). PR 본문에 "추가·변경한 API(ID, 경로)"를 적고 리뷰어에 범영을 넣는다. 범영은 리뷰에서 검수한다(ID 겹침·경로 규칙·상태 표시) |
| 새 API ID를 붙일 때 | 만든 사람 | 그 장의 앞글자(AUTH·DIAG·SIM …)를 쓰고 마지막 번호 다음을 쓴다. 기존 API를 대신하는 경로면 새 번호를 만들지 않고 그 행을 고친다(예: DIAG-04) |
| 정의서 1장(공통 규칙·오류 code 표)·장 구성, 아래 3장 | 팀 합의 후 범영 | 바꾸면 세 팀 명세서에 영향이 있어 먼저 알린다. 새 오류 code가 필요하면 PR 본문에 적고 범영이 1장 표에 넣는다 |

- 11/20부터 정의서 2장 행은 만든 사람이 고친다(전에는 범영이 모아서 반영해 정의서가 코드보다 늦었다. 예: DIAG-01·04).
- 바뀐 곳에는 `🆕 MM/DD`를 붙이고, 문서 맨 위 「최근 변경」에 한 줄 요약한다. 다음 갱신 때 이전 표시는 지우고 "이전 변경" 한 줄로 줄인다.
- 상태 표시: ✅ 구현됨·확정 · 🟡 제안·임시 · ⛔ 만들지 않음·미정
- 개인정보·비밀값(IP, 이메일, 키, 실제 회원 값)은 예시에도 넣지 않는다.

## 3. 명세서 작성 규칙 (세 팀 공통)

C팀 문서(FP-203, 광희)에서 처음 쓴 양식을 공통으로 쓴다. 더 자세한 공통 규칙은 [정의서](api_definition.md) 1장에 있다.

- 성공 응답은 본문을 감싸지 않고 그대로 보낸다.
- 오류 응답은 백엔드 공통 형식 `{ "code", "message", "fieldErrors": [{ "field", "message" }] }`이다(`backend/.../global/exception`, `backend/README.md`). 🟡 decisions.md D-20은 아직 "미정"이다.
- 입력 오류는 `400 INVALID_INPUT`이고 어느 칸인지 `fieldErrors`에 담는다. 그 밖의 오류 code는 정의서 1-1(A팀)·1-2(C팀), B팀 명세서 3장·4장에 있다.
- 금액은 원 단위 정수, 비율은 % 단위 소수(소수 둘째 자리), 기준월은 `"YYYY-MM"`, 시각은 ISO-8601 + `+09:00`이다.
- Java DTO의 `boolean isXxx` 필드는 JSON에서 **`is`가 빠진 `xxx`**로 나간다(Lombok·Jackson 규칙). 예: `isHighVolatility` → `highVolatility`.
- API마다 적을 것: 메서드·경로, 인증, 요청(쿼리·본문 필드 표: 이름·형식·필수·설명), 응답 예시 JSON과 필드 표(관련 N-ID 포함), 오류 표(HTTP·code·언제).
