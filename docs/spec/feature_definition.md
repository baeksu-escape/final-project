- v0.3 변경(11/13): 데이터 담당 답변을 반영해 기존 모델 피처를 16개에서 19개로 늘렸다. 신용평가사 207열 중 화면 입력과 맞는 7개만 남기고 나머지는 보류(4장)한다.

## 1. 개요

이 문서는 모델이 입력으로 쓰는 피처(열)의 이름, 뜻, 원천, 계산식, 단위, 0·결측 처리, 대안 데이터 여부를 정한다.
`DIM_FEATURE`(피처 코드·이름·단위·`ALTERNATIVE_YN`·`SIMULATABLE_YN`·표시 순서)와 `ASSESSMENT_FACTOR`(SHAP 요인)에 넣을 값의 근거가 된다.

| 구분 | 기존 집단 | 씬파일 집단 |
|---|---:|---:|
| 모델 표 열 수 | 252 | 261 |
| 모델 입력 피처(`role=feature`) | 235 | 243 |

위 표는 학습 데이터 묶음 전체의 열 수다. **서비스 모델이 실제로 쓰는 피처는 아래 두 모델이며, 대안 모델 기준 38개다.**

| 모델 | 구성 | 피처 수 |
|---|---|---:|
| 기존 모델 | 화면에서 받는 전통 신용평가 항목만 사용 (소득·지출·상환 9, 프로필 3, 신용 이력 6) — 3장 | 18 |
| 대안 모델 | 기존 모델 피처 + 대안 데이터 5종 — 3장 | 18 + 20 = 38 |

- 기존 모델은 "신용평가사의 기존 점수"가 아니라 **기존 신용평가에서 주로 쓰는 항목으로 만든 모델**이다. 두 모델의 점수를 비교하는 것이 서비스의 중심 기능이다.
- 대안 데이터 20개: 통신·공과금 3, 간편결제 4, 국민연금 6, 건강보험 6, `si_arrears_any` 1.
- 서비스 38개는 `model_table_columns.csv`의 `role=feature` 235개(씬파일 243개) 중에서 화면 입력에 대응하는 열만 고른 **서비스용 선택 목록**이다. 두 목록은 서로 다르다. 235·243개 전체가 서비스 피처인 것이 아니다.
- 열 역할의 정본은 학습 데이터 묶음의 `1_model/model_table_columns.csv`다. 이 문서는 그 내용을 사람이 읽기 쉽게 풀어 쓴 것이다.
- 통계는 `1_model/legacy_model_table.csv`(기존 집단)와 `thinfile_model_table.csv`(씬파일 집단)에서 계산했다. 데이터가 다시 생성되면 숫자를 갱신한다.

## 2. 열의 역할

| 역할 | 열 | 모델 입력 |
|---|---|---|
| `feature` | 3장의 열(서비스 모델이 쓰는 38개). 4–5장의 열은 보류 | 3장은 예, 4–5장은 지금 서비스에서는 아니오 |
| `label` | 기존 모델의 정답 `label_any_delinquency_12m`, 대안 모델의 정답 `label_nonfin_effect_12m`(2-1 참고). 두 라벨은 서로 다르다 | 아니오 |
| `id` / `group` / `split` | `customer_id`, `dataset`, `cohort`, `data_split` | 아니오 |
| `compatibility_only` | 6개월 집계 11열(`income_6m_krw` 등) | 아니오(보존·참고용) |
| `eval_only` | `eval_future_credit_exposure`(씬파일) | 아니오(씬파일 학습·평가 대상을 거르는 데만 사용) |

### 2-1. 정답 라벨과 두 모델의 AUC를 비교하는 방법

| 모델 | 정답 라벨 | 정의 |
|---|---|---|
| 기존 모델(18개) | `label_any_delinquency_12m` | 가상 향후 12개월에 연체가 1개월 이상 있으면 1, 없으면 0(데이터 사전: "기존 미래 연체월 수 > 0"). 학습 데이터 생성 코드가 만든 열이고 이 문서나 학습 코드가 규칙을 다시 계산하지 않는다 |
| 대안 모델(38개) | `label_nonfin_effect_12m` | 위 연체 라벨의 로짓에 비금융 효과를 더해 만든 **별도 합성 라벨**이다. 통신·공과금 미납(승산비 2.5), 현금흐름 압박(약하게), 사회보험 비정시 납부(승산비 2.0), 간편결제 규칙성(약한 감점 효과)이 들어 있다. 출처: `fastapi_server/data_generation/docs/NONFINANCIAL_LABEL.md` |

- 두 라벨 값은 VALID 1,800행에서 83.2%만 같다. 그래서 **서로 다른 라벨로 잰 AUC를 그대로 빼서 비교하지 않는다.** 두 모델을 두 라벨에서 각각 평가해 같은 라벨끼리 비교한다. 재현: `fastapi_server/training/compare_labels.py`.
- 같은 라벨로 맞춘 비교(VALID, 시드 5개 평균 ± 표준편차, LightGBM 4.6.0 고정 설정, 튜닝 없음, 11/17):

| 평가 라벨 | 기존 18개 | 대안 38개 | 대안 − 기존 |
|---|---|---|---|
| `label_any_delinquency_12m`(연체 경험) | 0.6049 ± 0.0026 | 0.5991 ± 0.0124 | −0.006 (시드별 −0.015 ~ +0.012, 차이 없음) |
| `label_nonfin_effect_12m`(비금융 효과 라벨) | 0.6102 ± 0.0016 | 0.6533 ± 0.0051 | +0.043 (시드별 +0.038 ~ +0.048) |

- **어떻게 설명하나:** 연체 경험 라벨에서는 대안 데이터를 넣어도 성능이 오르지 않는다(데이터 README의 "효과를 넣지 않으면 차이가 없다"와 같다). 비금융 효과를 넣은 라벨에서는 대안 모델이 약 0.04 높다. 이 차이는 **라벨에 가정으로 넣은 효과를 모델이 찾아낸 것**이며, 실제 대출 시장에서 대안 데이터가 성능을 올린다는 증거가 아니다.
- 해석 한계: 합성 데이터, 합성 라벨, 튜닝 없음, 시드 5개, VALID 기준이다. TEST는 최종 평가(FP-144)에서 한 번만 쓴다. 점수나 AUC를 실제 신용평가 결과처럼 쓰지 않는다.

## 3. 서비스 모델 피처 (기존 모델 + 대안 모델)

회원이 화면에서 직접 입력하거나 대안 데이터 API(통신·공과금·간편결제·국민연금·건강보험, 더미)로 받는 값에서 만들어지는 피처다.
`통계`는 기존 집단 12,000행 기준이다. 결측 수는 괄호 안에 적었다.

| 소절 | 내용 | 기존 모델 | 대안 모델 | 피처 수 |
|---|---|:---:|:---:|---:|
| 3-1 | 소득·지출·상환 (12개월, 서비스 정의) | 예 | 예 | 9 |
| 3-2 | 납부 이력: 통신·공과금 | 아니오 | 예 | 3 |
| 3-3 | 간편결제 | 아니오 | 예 | 4 |
| 3-4 | 국민연금·건강보험 | 아니오 | 예 | 13 |
| 3-5 | 프로필 | 예 | 예 | 3 |
| 3-6 | 신용 이력(화면 입력과 대응하는 207열 7개 중 6개 사용) | 예 | 예 | 6 |

- 3-5의 `debt_balance_krw`는 기존 모델 피처이고, 3-5의 `segment`, `age`도 기존 모델 피처다.
- 기존 모델 합계: 3-1(9) + 3-5(3) + 3-6(6) = 18. 대안 모델 합계: 18 + 3-2(3) + 3-3(4) + 3-4(13) = 38. 3-6의 `LRZ021201`은 11/16 임시 결정으로 모델에서 뺐다(10장 C9).
- 3-4의 13개는 국민연금 6 + 건강보험 6 + `si_arrears_any` 1이다.

### 3-1. 소득·지출·상환 (12개월, 서비스 정의)

원천: 회원 입력. 소득은 12개월 월별 입력(급여소득자는 기준월 1개월 값 × 12), 지출은 평균 월 지출 1개, 상환은 현재 월 상환액 1개.
기준월은 원천 마지막 달인 2026-08이며, 급여소득자 기준월은 팀 확인 전 임시값이다.

| 피처 코드 | 뜻·계산식 | 단위 | 통계 (최솟값 / 중앙값 / 최댓값) |
|---|---|---|---|
| `income_svc_12m_krw` | 12개월 소득 합계 | 원 | 1,053,084 / 37,087,830 / 145,743,804,000 (결측 120) |
| `income_cv_svc_12m` | 12개월 월소득의 표준편차 ÷ 평균 | 소수 | 0 / 0 / 1.214 (0인 행 9,410) |
| `zero_income_months_svc_12m` | 12개월 중 월소득이 0인 달 수 | 개월 | 0 / 0 / 4 |
| `expense_avg_month_krw` | 평균 월 생활지출 (정확히 .5이면 올림, `ROUND_HALF_UP`) | 원 | 212,743 / 1,505,780 / 8,029,802,000 (결측 120) |
| `debt_service_current_krw` | 현재 월 상환액(기준월 상환액) | 원 | -8,316,666 / 548,667 / 71,726,583 (결측 120, 0인 행 1,088) |
| `expense_ratio_svc_12m` | 평균 월 지출 × 12 ÷ 12개월 소득 합계 (합계가 0 이하이면 값을 만들지 않음) | 소수 | 0.022 / 0.532 / 3.033 |
| `dsr_svc_12m` | 현재 월 상환액 × 12 ÷ 12개월 소득 합계 (합계가 0 이하이면 값을 만들지 않음) | 소수 | 0 / 0.163 / 21.53 |
| `deficit_months_svc_12m` | 12개월 중 (월 소득 − 평균 월 지출 − 현재 월 상환액) < 0인 달 수 | 개월 | 0 / 0 / 12 |
| `worst_month_net_cash_svc_12m_krw` | 12개월 중 가장 낮은 달의 (월 소득 − 평균 월 지출 − 현재 월 상환액) | 원 | -55,666,388 / 309,047 / 25,555,978 |

- `ALTERNATIVE_YN` 제안: 아니오. `SIMULATABLE_YN` 제안: 아니오(금액 입력 4개와 다른 항목이다).
- 상환 부담률에 해당하는 열은 `dsr_svc_12m` 하나뿐이다(`expense_ratio_svc_12m`은 지출 비율이다). 명세 N-16-1·N-20-4는 상환 부담률(DSR)을 같은 함수로 계산한다고 했는데, `dsr_svc_12m`과는 차이가 있다. N-20-4는 (연간 원리금 상환액 ÷ 연소득) × 100(% 단위, BigDecimal 반올림, 연소득 0원이면 오류 방지)이고, `dsr_svc_12m`은 현재 월 상환액 × 12 ÷ 12개월 소득 합계(소수 단위, 소득이 0이면 값을 만들지 않음)다. 같은 계산으로 맞출지는 팀이 정한다(9장).
- 이 9열은 이상치 처리가 필요하다(7장). 소득 최댓값이 약 1,457억 원, 지출 최댓값이 약 80억 원, 상환액 최솟값이 음수인 것은 데이터에 주입된 이상치다.

### 3-2. 납부 이력 (대안 데이터: 통신·공과금)

| 피처 코드 | 뜻 | 단위 | 통계 |
|---|---|---|---|
| `telecom_late_months` | 12개월 중 통신비 미납 달 수 | 개월 | 0–5, 0인 행 93.2% |
| `utility_late_months` | 12개월 중 공과금(전기·가스·수도 합산) 미납 달 수 | 개월 | 0–5, 0인 행 93.7% |
| `telecom_on_time_streak` | 관측된 최근 12개월 창 내 연속 정시 납부 개월 수 | 개월 | 0–12, 중앙값 12 |

- 설정 범위는 0–12이지만 생성된 미납 달 수는 0–5까지다.
- **미납 달 = `LATE` + `UNPAID`.** 통신비·공과금에는 일부 납부(`PARTIAL`) 상태가 없다(DDL은 `ON_TIME`/`LATE`/`UNPAID`만 허용, 학습 생성 코드는 달마다 연체 여부만 만든다). 국민연금·건강보험(3-4)은 `PARTIAL`도 체납으로 세지만 통신비·공과금에는 적용하지 않는다. FP-140 예측 Mock이 이 방식으로 센다.
- `ALTERNATIVE_YN` 제안: 예(3개 모두).
- `SIMULATABLE_YN` 제안: 예 — `telecom_on_time_streak`(통신비 정시 납부 기간 슬라이더), `utility_late_months`(공과금 미납 개월 수 슬라이더). `telecom_late_months`는 `telecom_on_time_streak`와 한 쌍으로 같이 움직이므로 시뮬레이터에서 어떻게 다룰지 8장에서 정한다.

### 3-4. 국민연금·건강보험 (대안 데이터)

국민연금(`np_`)과 건강보험(`hi_`)은 같은 구조의 열을 가진다.

### 3-7. 계산 세부 규칙 (서비스에서 피처를 계산할 때)

서비스(예: `fastapi_server/pipeline/feature_builder.py`)가 학습 때와 같은 값을 만들도록, 학습 데이터 생성 코드(`generate/input_feature_logic.py`, `generate/nonfinancial_sources.py`)와 학습 데이터 v3.6.1을 확인한 결과다(11/16). **학습 정의**는 확인한 사실이고, **서비스 규칙**은 학습에 없는 경우를 위한 제안이므로 팀 확인이 필요하다.

**① 소득 변동 정도 `income_cv_svc_12m`**
- 학습 정의: 표준편차는 **모집단 방식**(12로 나눔, `std(ddof=0)`)이고, 평균으로 나눈다.
- 평균이 0 이하이면 값을 만들지 않는다(결측). `dsr_svc_12m`, `expense_ratio_svc_12m`도 12개월 소득 합계가 0 이하이면 결측이다.

**② 국민연금·건강보험 가입 상태·유형 `np_/hi_coverage_status`, `np_/hi_payer_type`**
- 학습 정의: 보험별 **첫 행**의 값이다. 학습 데이터에서 이 값은 12개월 동안 달라지지 않는다(12,000명 × 2종 확인, 고객·보험별 서로 다른 값 수가 최대 1). 그래서 어느 달을 써도 같다.
- 서비스 규칙(제안): 기관 응답에서 달마다 값이 다르면 **가장 최근 달**의 값을 쓴다.
- 학습 데이터에 없는 값: 가입 상태 `UNKNOWN`, 납부 유형 `VOLUNTARY`는 DDL과 생성 코드가 허용하지만 학습 데이터(3-4 통계)에는 한 번도 나오지 않는다. 서비스에서 들어오면 모델이 처음 보는 범주이므로, 처리 방식(다른 값으로 바꿈, 결측 처리 등)은 정해지지 않았다(9장).

**③ 납부 대상 개월 `np_/hi_due_months`와 관련 열**
- 학습 정의: 납부 상태가 `on_time`·`late`·`partial`·`unpaid`인 달만 센다. `not_due`(납부 기한 전), `not_applicable`(대상 아님), `unknown`(확인 불가)은 세지 않는다.
- `*_on_time_months` = `on_time`인 달 수. `*_arrears_months` = `late`·`partial`·`unpaid`인 달 수. `*_on_time_rate` = `on_time_months` ÷ `due_months`이고, `due_months`가 0이면 결측이다.
- 학습 데이터(12,000명)의 납부 상태는 `on_time`, `not_applicable`, `unpaid`, `late`, `partial` 다섯 가지뿐이고 `unknown`과 `not_due`인 달은 **없다**. 그래서 `unknown`을 세지 않는 것은 코드 구조에서 나온 규칙이며 학습으로 검증된 값은 아니다. 서비스에서 `unknown`이 많으면 `due_months`가 줄거나 0이 되어 `on_time_rate`가 결측이 된다.

**④ 간편결제 `dp_*`**
- 학습 정의: `dp_active_months` = 결제 건수가 0보다 큰 달 수. `dp_payment_count_12m`, `dp_payment_amount_12m_krw` = 12개월 합계.
- 학습 데이터의 월별 기록 상태는 `observed`(결제 있음)와 `no_activity`(결제 없음) 두 가지뿐이고 **빈 값(`missing`)인 달은 없다.** `no_activity`인 달은 건수·금액·이용일이 빈 값이 아니라 **0**이다.
- 서비스 규칙(제안): 기록이 비어 있는 달(`MISSING`)은 0으로 치지 않고 합계에서 **건너뛴다.** 합계와 `dp_active_months`는 0으로 본 것과 결과가 같다.
- **`dp_ever_used`는 결제 기록에서 계산한 값이 아니다.** 학습 데이터 생성 때 사람마다 "사용자인지"를 먼저 뽑은 값이다. 그래서 `dp_ever_used = 1`인데 12개월 결제가 0건인 사람이 74명(12,000명 중 0.6%) 있다. 반대로 `dp_ever_used = 0`인데 결제가 있는 사람은 없다. 서비스에는 "사용자인지" 정보가 없으므로 대용치가 필요하다.
- **서비스 규칙(1차 확정, C11): `dp_ever_used` = 12개월 결제 건수 > 0이면 1, 아니면 0.** 학습값과 0.6%(사용자인데 결제 0건인 74명)만 다르다. 결제 0건인 사용자는 서비스에서 0이 된다.
- 간편결제 연결·동의 여부로 정하지 않는다. 점수 산출에 대안 데이터 5종 동의가 모두 필요해서(8-3) 서비스에서는 항상 1이 되고, 학습에서 0인 15%의 구분이 사라진다. 기관 응답 더미에도 계정 유무 값이 없다. 2차에서 기관 mock 서버를 API로 바꿀 때 간편결제 응답에 계정 유무를 넣으면 그때 연결·동의 여부 방식으로 다시 검토한다.

## 7. 전처리 규칙

1. **0과 결측을 구분한다.** 0은 유효한 값(예: 미납 0개월, 대출 0건)이다. 결측(null)을 0으로 채우지 않는다.
2. **구조적 결측.** `np_on_time_rate`, `hi_on_time_rate`는 납부 의무 달 수(`*_due_months`)가 0이면 정시 납부율을 계산할 대상이 없어 NULL이다(데이터 담당 확인, 기존 집단 12,000행에서 국민연금 2,974행·건강보험 492행이 `due_months=0`과 일치). 0%나 100%로 단정하지 않는다. 데이터 담당 권고: 결측을 직접 처리하는 모델과 결측 지시 열을 함께 쓰는 보정을 비교한다. 중앙값 보정은 두 비율의 중앙값이 1.0이라 100%로 채워지므로 주의한다. 국민연금은 `np_coverage_status`가 이미 있어 별도 지시 열이 필요한지 확인한다. **임시 결정(11/16): 결측을 채우지 않고 모델(LightGBM)이 직접 처리한다.** 서비스(`feature_builder.py`)도 `due_months`가 0이면 결측으로 두므로 학습과 같다. 비교와 대안은 10장 C13에 남겼다.
3. **주입된 결측.** `income_svc_12m_krw`, `expense_avg_month_krw`, `debt_service_current_krw`는 기존 집단에서 각각 120행(1.0%) 결측이다. 데이터 담당 확인: 파생 열(`income_cv_svc_12m`, `expense_ratio_svc_12m`, `dsr_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw`)을 **먼저 만들고** 세 입력 열에 시연용 결측·이상치를 주입했다. 그래서 파생 열은 주입 전 값이고 결측이 없으며, 입력 열과 값이 어긋날 수 있다. CV·소득 0인 달 수·부족 달 수·최악 월 현금흐름은 월별 원천이 있어야 재계산되며 세 입력 열만으로는 만들 수 없다.
   - **서비스와의 차이:** 서비스는 회원이 입력한 같은 값으로 파생 열을 계산하므로, 입력 열과 파생 열이 항상 일치한다. 학습 데이터는 주입 때문에 어긋난 행이 있다.
   - **학습 전처리 기준 — 임시 결정(11/16): (나).** 베이스라인에서 시험한 (나)는 아래 문장 그대로 다시 계산한 것이 아니라 서비스와 같게 "걸러진·결측인 입력과 그 입력으로 만드는 파생 열(`income_cv_svc_12m`, `expense_ratio_svc_12m`, `dsr_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw`)을 결측으로 두는" 방식이다(월별 원천이 없어 재계산이 안 되는 열이 있기 때문). 결정 근거와 되돌리는 방법은 10장 C19. 선택지 원문: (가) 주입 전 원천 기준으로 파생 열을 그대로 쓰고 세 입력 열만 보정한다 / (나) 보정한 입력 열로 파생 열(`expense_ratio_svc_12m`, `dsr_svc_12m` 등)을 다시 계산한다. 월별 원천이 필요한 열은 (나)로 다시 계산할 수 없다. 선택에 따라 학습 분포와 서비스 입력의 일치 정도가 달라진다.
   - **서비스 구현(FP-140 예측 Mock, 11/16 기준):** 이상치(4번)로 걸러진 값과 그 값으로 만드는 비율 피처(`expense_ratio_svc_12m`, `dsr_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw`, `income_cv_svc_12m` 등)를 모두 결측으로 둔다. 동작은 위 (나)에 가깝다(다시 계산하지 않고 결측으로 둔다). 어떤 값이 걸리면 무엇이 결측이 되는지: 소득 합계 > 20억 → `income_svc_12m_krw`, `income_cv_svc_12m`, `expense_ratio_svc_12m`, `dsr_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw` / 평균 월 지출 > 2억 → `expense_avg_month_krw`, `expense_ratio_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw` / 월 상환액 < 0 → `debt_service_current_krw`, `dsr_svc_12m`, `deficit_months_svc_12m`, `worst_month_net_cash_svc_12m_krw`, `LRZ021201`(Mock의 FS-DRAFT 39개 기준이며, 이 문서의 38개에서는 C9로 모델에서 뺐다). `zero_income_months_svc_12m`(큰 값이 있어도 셀 수 있음)와 `debt_balance_krw`(상한 검사 없음)는 결측으로 만들지 않는다. 이것은 서비스 동작이고, 학습 전처리 기준은 위 (나)로 임시 결정했다(C19).
4. **이상치.** 소득·지출은 0.5%에 1,000배, 상환액은 0.3%에 음수가 주입되어 있다(`anomaly_log_12m_svc.csv`). 이 기록은 전처리 평가용 정답지이며 학습·모델 입력에 쓰지 않고, 서비스 추론에는 이 기록이 없다. 데이터 담당 권고: 입력 검증 기준으로 잘못된 값을 결측 처리하고, 학습 분할에서만 정한 보정 규칙을 평가·추론에도 같게 적용한다. DDL은 소득·지출·월 상환액의 음수를 금지한다. 큰 소득을 이상으로 보는 업무상 상한과 Spring 검증 구현은 확인되지 않았다. 최종 방식은 B팀 결정(미정).
5. **급여소득자 소득.** 기준월 소득 × 12로 펼친다. 이때 `income_cv_svc_12m`은 0, `zero_income_months_svc_12m`은 0이 된다(기존 집단 9,410행이 0).
6. **금액 단위.** 학습 데이터의 신용평가사 값은 천원, 서비스 입력과 DB는 원이다. `LA0099212`는 학습값에 1,000을 곱해 원 단위로 통일하고, 학습·추론 양쪽 단위를 동일하게 관리한다(데이터 담당 확인). `LRZ021201`(천원/년)도 같은 방식으로 통일한다. `debt_balance_krw`는 학습 데이터에서 `L00000002` × 1,000으로 만들었다.
7. **학습·평가 구분.** `data_split`(TRAIN/VALID/TEST = 70/15/15, 고객 ID 단위, 직군 × 연체 라벨 층화)으로 나누고, 성능 비교는 TEST만 쓴다.

### 8-5. 대안 데이터가 빈 목록일 때 ((다) 1차 확정, 구현 담당 확인 필요)

**상황.** 5종 동의 후 불러왔는데 기관에 그 계정의 기록이 없으면 서비스는 0건(빈 목록)으로 불러온다(A팀 `missing-member-mode=EMPTY`). 시드 회원 400명은 기록이 모두 있고, 시드에 없는 새 계정이 해당한다. 시드 SQL은 318명분이고 기관 응답 파일은 400명분인데, 차이 82명은 시작 동의 상태가 0인 비동의 회원이라 시드 행이 없는 것이다. 동의 후 불러오면 응답 파일에서 행이 생긴다(A팀 확인).

**지금 동작(FP-140 작성자가 직접 실행해 확인).** 빈 목록을 보내면 오류 없이 200으로 점수가 나온다.
- 통신비·공과금: 미납 개월 0, `telecom_on_time_streak` 0
- 간편결제: 4개 열 모두 0(`dp_ever_used` 포함)
- 국민연금·건강보험: 가입 상태·유형·정시 납부율은 결측, 납부 대상·정시·미납 개월과 `si_arrears_any`는 0
- 테스트에 빈 목록 케이스는 없다.

**학습과의 차이.**
- 통신비·공과금은 학습 12,000명 모두 기록이 있다. 기록 없음은 학습에 없는 입력이다.
- `telecom_on_time_streak` 0은 학습에서 99명(0.8%)이고 "마지막 달이 연체"라는 뜻이라 기록 없음의 0과 뜻이 다르다.
- 간편결제 결제 0건은 학습에 1,878명(15.7%)이라 정상 입력이다. 보험 납부 대상 0개월도 학습에 있다. 단 보험 가입 상태·유형이 빈 경우는 학습에 없고 아직 정하지 않았다.

**후보.**
| 후보 | 내용 | 필요한 일 |
|---|---|---|
| (가) | 기록 없는 피처를 결측으로 둔다 | 통신비·공과금이 결측인 학습 데이터와 재학습. LightGBM은 학습에서 결측을 못 본 피처의 결측을 보통 0으로 취급하므로 서버만 None으로 보내서는 효과가 없다(일반 동작이며 이 모델로 확인하지 않았다) |
| (나) | 지금처럼 0으로 둔다 | 없음. 단 연체 0개월(좋은 신호)과 연속 정시 0개월(나쁜 신호)이 충돌해 점수 방향을 알 수 없다 |
| (다) | 기록 없는 계정은 점수를 내지 않는다 | 아래 |

**1차 확정(11/16, B팀 정의서 담당): (다).** 통신비 또는 공과금이 빈 목록이면 점수를 내지 않고 산출 불가로 처리한다. 변경 기록은 10장 C14, C16. 확정에 따라 필요한 일(구현 담당은 확인 필요):
1. `DIM_NOT_SCORABLE_REASON`에 사유 코드 1행 추가(코드 `ALT_DATA_EMPTY`, 표시 이름 "통신비·공과금 기관 기록 없음", 11/16 B팀 정의서 담당이 정함. FP-142 작성자에게 알림 필요, Spring 선검사가 그 코드를 쓴다). B팀 정의서 담당이 `avenue_ddl.sql`과 사본 `dummy_db/01_create_tables.sql` 두 파일에 똑같이 넣어(두 파일은 바이트까지 같게 유지한다, `docs/spec/sql/README.md`) PR로 올리고 작업 로그를 남긴다(DB 기준 데이터 변경).
2. Spring이 호출 전에 통신비·공과금 목록이 비었는지 검사해 산출 불가로 저장한다. 빈 결과를 구분하는 저장 컬럼은 없고 행이 0개인지 세면 된다. 지금 Spring은 입력 완료 현황만 본다. FastAPI도 422로 한 번 더 막는 쪽이 안전하다는 의견이다(FP-140 작성자). FastAPI만 막으면 Spring이 4xx를 모델 오류로 저장해 회원에게 모델 오류로 보인다. 확정되면 Spring 쪽은 FP-142 작성자가 맡는다.
3. 화면에 산출 불가 이유를 알리는 안내 문구(UI 담당).

**시연.** 신규 가입은 보여 주되 점수 산출은 미리 준비한 계정으로 한다(11/16, B팀 정의서 담당 결정). 시연에서 `BORROW`는 쓰지 않고 기본 `EMPTY`를 유지하며, 준비한 계정은 기관 기록이 있어 (다)에 걸리지 않는다. `BORROW`는 같은 직군 더미 회원 중 사용자 ID 순서로 고른 한 명의 응답을 새 계정의 행으로 저장하고(무작위 아님) 빌린 원천 회원의 ID·이름은 저장하지 않는다. 신규 가입 계정으로 점수까지 시연한다는 계획과 `BORROW`를 쓰기로 한 팀 결정은 저장소 문서에 없다. 준비한 계정의 시드 변경은 필요하면 나중에 정한다.

## 11. DIM_FEATURE 입력용 표 (FS-V1 제안)

`DIM_FEATURE`(`FEATURE_SET_VERSION`, `FEATURE_CODE`, `FEATURE_NAME`, `UNIT_NAME`, `ALTERNATIVE_YN`, `SIMULATABLE_YN`, `DISPLAY_ORDER`)에 넣을 값이다. 피처 세트 버전은 `FS-V1`로 제안한다.
**코드·단위·`ALTERNATIVE_YN`은 위 정의를 따른다. 표시 이름, `SIMULATABLE_YN`, 표시 순서는 B팀의 제안이며 검토가 필요하다.** 표시 이름은 화면의 SHAP 요인 목록에 나타나므로 UI 담당 의견을 받는다.

- `FEATURE_CODE`는 학습 데이터의 열 이름 그대로 쓴다(`VARCHAR2(50)` 이내).
