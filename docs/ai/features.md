## 2. 기능 상세

### N-01 로그인·로그아웃 (일반·관리자 공통) · 회원·인증 · P0
일반 사용자와 관리자가 같은 로그인 화면을 쓰고, 역할에 따라 첫 화면이 정해진다. 로그인 화면은 메인(홍보) 페이지와 따로 둔다(N-10).

#### N-01-1 로그인 · P0
- 설명: 아이디와 비밀번호로 로그인한다.
- 입력: 아이디, 비밀번호
- 처리: 계정과 비밀번호를 확인하고 인증 토큰을 발급한다. 실패하면 아이디와 비밀번호 중 무엇이 틀렸는지 알려 주지 않는다.
- 출력: 로그인 성공(토큰 발급), 실패 시 오류 안내
- 테이블: app_user
- 비고: 인증 방식은 토큰으로 확정(10/30, D-06). 소셜 로그인은 N-01-6으로 따로 둔다. 2단계 인증은 제외(P3).
- ⚠️ UI: **관리자** 로그인에는 휴대폰 6자리 인증번호 2단계 인증이 있다. 일반 사용자는 2단계 인증이 없다 → decisions.md
- DDL v0.3.2: 관리자 로그인용 인증번호는 `verification_code`(목적 ADMIN_LOGIN)에 저장한다. 보내는 채널은 이메일·휴대폰 모두 허용되어 있고 아직 정해지지 않았다. 관리자 계정은 휴대폰을 비워 둘 수 있다.

#### N-01-2 역할별 첫 화면 이동 · P0
- 설명: 로그인한 계정의 역할에 따라 이동할 화면을 정한다.
- 입력: 로그인 계정(토큰)
- 처리: 계정의 역할(일반 또는 관리자)을 확인한다. 일반 사용자는 신용 리포트, 관리자는 모형 성능 비교로 보낸다. 직군을 고르지 않은 사용자는 직군 선택(N-05-1)으로 먼저 보낸다.
- 출력: 역할별 첫 화면
- 테이블: app_user
- 비고: 화면 분기 규칙은 N-08과 함께 쓴다.
- ⚠️ UI: 직군은 골랐지만 점수를 아직 산출하지 않은 사용자는 데이터 입력(N-05)으로 보낸다.

#### N-01-3 잠긴 계정 안내 · P0
- 설명: 잠긴 계정은 로그인을 막고 안내한다.
- 입력: 로그인 시도
- 처리: 계정 상태가 잠김이면 토큰을 발급하지 않는다.
- 출력: 잠금 안내 문구
- 테이블: app_user
- 비고: 계정 잠금은 관리자 기능 N-27-3에서 설정한다.
- ⚠️ UI: 비밀번호를 **5회 틀리면 자동으로 잠기고**, 비밀번호 찾기(N-03)로 재설정하면 풀린다. 관리자도 수동으로 잠그고 풀 수 있다.

#### N-01-4 로그아웃 · P0
- 설명: 로그인 상태를 끝낸다.
- 입력: 로그아웃 버튼
- 처리: 인증 토큰을 폐기하고 로그인 화면으로 보낸다.
- 출력: 로그인 화면
- 테이블: app_user

#### N-01-5 시연용 데모 계정 진입 · P0
- 설명: 시연 때 비밀번호 없이 데모 계정으로 들어간다.
- 입력: 데모 계정 선택
- 처리: 미리 만든 데모 계정으로 바로 로그인 상태를 만든다.
- 출력: 데모 계정의 첫 화면
- 테이블: app_user
- ⚠️ UI: 비밀번호 없이 들어가지 않는다. 로그인 화면 '시연 계정'의 **[채우기]** 를 누르면 아이디·비밀번호가 채워지고, 이후는 일반 로그인이다(사용자 1개, 관리자 1개) → decisions.md

#### N-01-6 소셜 로그인 · (우선순위 비어 있음)
- 설명: 외부 소셜 계정으로 로그인한다.
- 입력: 소셜 로그인 제공자 선택(Google·카카오·네이버)
- 처리: 외부 인증을 진행하고, 연결된 서비스 계정이 있으면 토큰을 발급한다. 처음 연결하는 소셜 계정이면 기존 아이디·비밀번호로 연결하거나 새로 가입한다(이름·이메일을 가입 화면에 채워 넘긴다). 관리자 계정은 소셜 로그인을 쓸 수 없다.
- 출력: 로그인 성공(토큰 발급), 실패 시 오류 안내
- 테이블: user_social_account, app_user
- 메모: OAuth 2.0 기반 외부 인증 제공자(Google·카카오·네이버)를 통해 인증하며, 인증 성공 후 서비스 자체 토큰을 발급한다. 최초 로그인 시 회원가입 및 계정 연동 처리 필요. (11/05 소셜 로그인 추가)
- ⚠️ 시트에 우선순위가 비어 있다. UI에는 구현되어 있다. 사용 테이블은 DDL의 `USER_SOCIAL_ACCOUNT`에 맞춰 채웠다(11/12).

### N-02 회원가입 · 회원·인증 · P0
기본 개인정보와 필수 동의, 이메일 인증을 거쳐 계정을 만든다. 직군은 로그인 후 고른다(N-05-1).

#### N-02-1 가입 정보 입력·형식 검사 · P0
- 설명: 가입에 필요한 기본 개인정보를 받는다. 연령대로 비교 집단을 정한다.
- 입력: 이름, 닉네임, 휴대폰, 이메일, 비밀번호, 출생년도
- 처리: 입력 형식을 검사하고 비밀번호 규칙(8자 이상, 영문·숫자·기호)을 안내한다. 닉네임은 2~12자이며 다른 회원과 겹치면 막는다.
- 출력: 항목별 오류 안내
- 테이블: app_user
- 비고: 직군은 가입 때 받지 않는다(10/30, D-04). 취미·관심상품 입력은 추천 상품 기능을 만들 때만 필요하다. 닉네임은 신용 라운지(N-06)에서 이름 대신 보인다(11/06).
- ⚠️ UI: 비밀번호는 **영문과 숫자를 섞어 8자 이상**(기호 요구 없음). 출생연도는 **1930~2006**만 가입할 수 있다(생일은 따지지 않고 출생연도만 검사, DDL v0.3.2). 휴대폰은 DDL에서 비워 둘 수 있다. 비교용 연령 구간은 **20대·30대·40대·50대 이상** 4개 → decisions.md

#### N-02-2 필수 동의 · P0
- 설명: 개인신용정보 수집·이용에 동의해야 가입할 수 있다.
- 입력: 필수 동의 체크
- 처리: 필수 동의가 없으면 가입을 막는다. 동의 이력을 남긴다.
- 출력: (시트에는 "인증코드 발송·확인 결과" — N-02-3 내용이 잘못 들어간 것으로 보인다)
- 테이블: user_consent
- 비고: 동의 법적 최대 유효기간 1년.
- ⚠️ UI: 동의 항목은 **필수 2개**(서비스 이용약관, 개인정보 수집·이용) + **선택 1개**(점수 변동 알림·혜택 안내).

#### N-02-3 이메일 인증코드 발송·확인 · P0
- 설명: 이메일로 인증코드를 보내 본인 이메일인지 확인한다.
- 입력: 이메일, 인증코드
- 처리: 인증코드를 만들어 메일로 보내고, 입력값과 맞는지 확인한다.
- 테이블: verification_code
- 비고: 비밀번호 찾기(N-03-2)와 이메일 변경(N-04-3)에서 같은 기능을 쓴다. 이메일 인증 포함으로 확정(10/30, 투표 D5).

#### N-02-4 계정 생성·개인정보 암호화 저장 · P0
- 설명: 검사와 인증을 마친 정보로 계정을 만든다.
- 입력: N-02-1~3의 결과
- 처리: 비밀번호는 BCrypt 단방향 해시로 저장한다. 이름·휴대폰·이메일은 AES로 암호화해 저장하고, 검색이 필요한 이메일·휴대폰은 HMAC 값을 함께 저장한다. 화면과 로그에는 마스킹한 값만 보여 준다.
- 출력: 가입 완료 안내
- 테이블: app_user, user_consent
- 비고: 비밀번호 단방향 해시, 그 외 개인정보 암호화 저장으로 확정(10/30, 투표 D5).

### N-03 아이디·비밀번호 찾기 · 회원·인증 · P0
가입 정보로 아이디를 찾고, 비밀번호는 메일 인증코드로 재설정한다.

#### N-03-1 아이디 찾기 · P0
- 설명: 가입 정보로 아이디를 찾아 일부를 가려서 보여 준다.
- 입력: 가입 시 입력한 정보(이메일·휴대폰)
- 처리: 입력한 이메일·휴대폰의 HMAC 값으로 계정을 조회하고 아이디 일부를 마스킹한다.
- 출력: 마스킹된 아이디
- 테이블: app_user

#### N-03-2 비밀번호 찾기 본인 확인 · P0
- 설명: 아이디와 이메일로 계정을 찾고 메일 인증코드로 본인을 확인한다.
- 입력: 아이디([아이디 확인] 버튼), 이름, 이메일, 인증코드

- 테이블: app_user, verification_code
- 비고: 이메일 인증은 N-02와 함께 만든다(10/30, 투표 D5).

#### N-04-7 회원 탈퇴 · 미정
- 설명: 비밀번호를 확인한 뒤 탈퇴한다.
- 입력: 비밀번호
- 처리: 비밀번호를 확인하고 계정 상태를 탈퇴로 바꾼다. 이름·연락처 등 개인정보는 대체값으로 덮어쓰고, 회원 행과 진단 내역은 남긴다. 동의로 불러온 대안 데이터는 삭제하고 그 밖의 딸린 데이터는 보관한다. 소셜 연결과 인증 기록도 삭제한다(인증 기록은 회원 번호뿐 아니라 이메일·휴대폰 HMAC으로도 찾아서 지운다). 신용 라운지 글의 작성자는 '탈퇴한 회원'으로 표시한다.

- 테이블: app_user, user_social_account, verification_code (탈퇴 = 상태 변경: ACCOUNT_STATUS_CODE를 탈퇴로 바꾸고 회원 행 유지, 개인정보는 대체값으로 덮어씀)
- 비고: 탈퇴 회원의 평가를 통계(N-13, N-25, N-26)에 넣을지는 팀이 정해야 한다(상태값으로 구분 가능). 개인정보 대체값 규칙은 DDL의 `CK_APU_PII_BY_STATUS`가 지킨다(DDL v0.3.2 W1). 탈퇴 직후 같은 아이디·이메일·소셜 계정으로 다시 가입할 수 있다(재가입 제한 없음). 직접 입력한 데이터와 평가는 탈퇴 후 5년 보관한다.

#### N-04-8 직군 변경 · 미정

- 테이블: app_user, dim_worker_type
- ⚠️ UI: 직군을 바꾸면 소득을 다시 입력해야 한다고 경고한다.

### N-05 데이터 입력 화면 (소득, 대출, 자산, 월 지출) · 데이터 입력 · P0
로그인 후 고른 직군에 맞는 평가용 값을 입력하고, 대안 데이터는 모의 연동으로 불러온다.

#### N-05-1 직군 선택 · P0
- 설명: 데이터를 입력하기 전에 직군을 고른다. 직군을 아직 고르지 않은 사용자는 로그인 후 이 단계부터 시작한다.
- 입력: 직군 선택(급여소득자·자영업자·프리랜서)
- 처리: 직군이 없으면 직군 선택 화면을 먼저 보여 주고, 고른 직군을 저장한다. 저장한 직군에 따라 소득 입력 방식(N-05-2)이 달라진다.
- 출력: 직군 선택 화면
- 테이블: app_user, dim_worker_type
- 비고: 직군 3분류로 확정(10/30, D-03). 직군 선택은 로그인 후 진행(10/30, D-04). 직군 변경은 N-04-8.

#### N-05-2 직군별 소득 입력 · P0
- 설명: 직군에 맞는 방식으로 소득을 입력한다.
- 입력: 자영업자·프리랜서: 월별 소득. 급여소득자: 월급(보너스 제외)
- 처리: 소득을 기준월과 함께 저장한다. 연소득은 따로 받지 않고 월별 값으로 계산한다.
- 출력: 소득 입력 결과
- 테이블: user_income_month, dim_worker_type
- 비고: 연소득 집계 기준 확정(10/30, 투표 D9). 입력 데이터에 날짜 추가로 확정(10/30, D-16). 월 소득 입력 12개월 확정(11/09).
- ⚠️ UI: 소득 칸에 **재직·운영·활동 기간**도 받는다 → decisions.md

#### N-05-3 대출(기존 부채) 입력 · P0
- 설명: 보유한 대출을 목록으로 추가·삭제한다.
- 입력: 대출 종류, 잔액, 금리, 고정·변동, 남은 기간, 월 원리금
- 처리: 대출을 기준월과 함께 저장한다.
- 출력: 대출 목록
- 테이블: user_loan, dim_loan_type, user_consent
- 비고: 입력 항목은 보유 대출 표(N-16-4)에 보이는 항목에 맞췄다. 팀 확인 필요.

#### N-05-4 자산 입력 · P0
- 설명: 보유 자산을 입력한다.
- 입력: 자산
- 처리: 자산을 기준월과 함께 저장한다.
- 출력: 자산 입력 결과
- 테이블: user_asset_snapshot

#### N-05-5 지출 입력 · P0
- 설명: 월 고정 지출과 할부·정기결제를 입력한다.
- 입력: 월 고정 지출(식비·교통·공과금 등), 할부·정기결제(항목 추가·삭제)
- 처리: 지출을 기준월과 함께 저장한다.
- 출력: 지출 목록
- 테이블: user_expense_item
- 비고: 현금흐름·납부 조건 입력은 N-18, N-21에서 다룬다. '월 생활비'를 '월 고정 지출'로 이름 변경(11/06).

#### N-05-6 대안 데이터 모의 연동 · P0
- 설명: 간편결제, 통신비, 공과금, 국민연금·건강보험료 납부내역을 불러온다.
- 입력: 불러오기 버튼
- 처리: 외부 금융·통신사 API 대신 더미 데이터를 불러와 저장한다.
- 출력: 항목별 불러오기 결과
- 테이블: user_telecom_payment, user_easypay_usage, user_social_insurance_payment, user_utility_payment, user_credit_profile, user_loan, user_consent
- 비고: 직접 입력을 먼저 만들고 모의 연동을 얹는다. 외부 API는 더미 데이터로 연동(10/30, D-08). 대안 데이터는 처음 4종으로 확정했고(10/30, D-08·D-09) 공과금이 추가되어 5종이 되었다(11/12, DDL v0.3.1 U1). 학습용 데이터는 합성이다. 불러오기 전에 정보 제공 동의를 받는다(N-05-9).
- DDL v0.3.2: 공과금은 전기·가스·수도 합계를 월 1행으로 저장하고, 납부 상태는 ON_TIME(기한 안)·LATE(기한 뒤)·UNPAID(미납, 납부일 없음)로 구분한다. 기관 응답이 late인데 납부일이 없으면 UNPAID로 바꿔 저장한다. 모델에 쓰는 값은 12개월 중 LATE 또는 UNPAID인 달의 수(0~12)다. 더미 기관 응답은 통신비·공과금·간편결제·국민연금·건강보험료 모두 12개월분이다. 공과금 청구액·기한·납부일은 학습 데이터에 없는 가정값이고, 공과금 미납과 부도의 관계는 합성 데이터에서 가정한 관계이므로 발표에서 그렇게 밝힌다.

- 출력: 항목별 오류 안내, 저장 결과
- 테이블: user_income_month, user_loan, user_asset_snapshot, user_expense_item, user_telecom_payment, user_easypay_usage, user_social_insurance_payment, user_utility_payment

#### N-05-8 입력 완료 현황 · P0
- 설명: 어떤 항목을 입력했는지 보여 준다.
- 입력: 저장된 입력 데이터
- 처리: 항목별 입력 여부를 확인한다.

- 테이블: user_income_month, user_loan, user_asset_snapshot, user_expense_item, user_telecom_payment, user_easypay_usage, user_social_insurance_payment, user_utility_payment
- 비고: 월 소득 12개월 입력으로 확정(11/09).
- ⚠️ UI: 현황 항목은 소득(12개월)·기간·자산·카드/부채·지출·대안 데이터(5개 모두) 6개이고, **모두 차야 [점수 산출하기]** 가 열린다 → decisions.md

#### N-05-9 대안 데이터 정보 제공 동의 · 미정
- 설명: 대안 데이터를 불러오기 전에 항목별로 정보 제공 동의를 받는다.
- 입력: [불러오기] 버튼, 필수 동의 체크
- 처리: 제공 기관, 불러오는 항목, 이용 목적, 보관 기간을 보여 주고 필수 체크를 받은 항목만 불러온다. 동의 일자를 남기고, [연결 해제]를 누르면 동의를 거두고 그 동의로 불러온 데이터를 지운다.
- 출력: 동의 창, 항목별 동의 일자
- 테이블: user_consent, user_loan, user_telecom_payment, user_utility_payment, user_easypay_usage, user_social_insurance_payment, user_credit_profile
- 비고: 대안 데이터 5종(간편결제·통신비·국민연금·건강보험료·공과금)을 모두 동의하고 불러와야 점수를 산출한다. 하나라도 없으면 산출 불가이고 사유 코드는 CONSENT_REQUIRED다(11/12). 동의하지 않아도 가입은 할 수 있다.

### N-06 게시판 (신용 라운지) · 커뮤니티 · P2

### N-17 시나리오 테스트 (금리·소득·지출, 악화·호전) · 재무 진단 · P1
금리·소득·지출이 나빠지거나 좋아질 때 상환 여력이 어떻게 달라지는지 계산한다. (옛 이름: 스트레스 테스트)

#### N-17-1 저장 데이터 조회 · P1
- 설명: 현재 대출·소득·지출 값을 불러온다.
- 입력: 로그인 계정
- 처리: 현재 값을 DB에서 조회한다.
- 출력: 보유 대출(금리·방식·월 상환), 월 소득, 지출
- 테이블: user_loan, user_income_month, user_expense_item

#### N-17-2 시나리오 입력 · P1
- 설명: 금리·소득·지출의 변화 폭을 정한다.
- 입력: 상황 버튼(나빠지는 경우: 금리 +1·+2%p, 소득 −20%, 악화 복합 / 좋아지는 경우: 금리 −1%p, 소득 +10%, 지출 −10%, 호전 복합), 금리 변화(−2~+3%p), 소득 변화(−50~+30%), 지출 변화(−30~+30%)
- 처리: 상황을 고르거나 슬라이더를 움직이거나 숫자를 직접 입력한다. 직접 입력은 금리 −5~+10%p, 소득 −100~+100%, 지출 −50~+100%까지 받는다.
- 출력: 선택한 시나리오
- 테이블: fact_policy_rate
- 비고: 좋아지는 경우와 숫자 직접 입력을 추가(11/06).

#### N-17-3 공통 재계산 틀 · P1
- 설명: 바꾼 값으로 다시 계산하는 구조를 둔다.
- 입력: 현재 값, 바꾼 값
- 처리: 현재 값에 바뀐 값을 반영해 다시 계산한다. N-18, N-21과 같은 구조를 쓴다.
- 출력: 재계산 입력값
- 테이블: 없음

#### N-17-4 상환 여력 재계산 · P1
- 설명: 시나리오를 반영해 월 잉여와 상환 부담률을 다시 계산한다.
- 입력: 시나리오 반영 값, 정책금리, 대출
- 처리: 바뀐 금리·소득·지출로 월 잉여, 상환 부담률, 월 이자 변화를 계산한다. 돈이 모자라면 버틸 수 있는 개월 수를 구하고, 좋아지는 경우에는 지금보다 늘어나는 월 잉여를 구한다. 점수는 구하지 않는다.
- 출력: 월 잉여, 상환 부담률, 월 이자 변화(±), 지금 대비 월 잉여 차이, 버틸 수 있는 개월 수
- 테이블: user_loan, user_income_month, fact_policy_rate
- 비고: 점수 변화를 예측하는 기능은 N-21이고, 이 기능은 상환 여력을 본다.

#### N-17-5 현재·시나리오 비교 표시 · P1
- 설명: 현재와 시나리오 결과를 나란히 보여 준다.
- 입력: N-17-4 결과
- 처리: 현재 값과 시나리오 값을 나란히 표시한다.
- 출력: 월 잉여, 상환 부담률, 월 이자 변화(±), 지금 대비 월 잉여 차이, 버틸 수 있는 개월 수
- 테이블: 없음

### N-18 신용케어 시뮬레이터 (행동 예측형 신용·한도 분석기) · 시뮬레이터 · P1
납부·이용 행동을 바꾸면 점수가 어떻게 달라지는지, 그 점수대의 금리·한도와 맞는 더미 대출 상품을 보여 준다. (옛 이름: 점수·금리 시뮬레이터)

#### N-18-3 값 바꾸기 (금액 입력 4개) · P1

#### N-18-4 공통 재계산 틀 · P1
- 설명: 바꾼 값으로 다시 계산하는 구조를 둔다.
- 입력: 내 실제 값(DB에서 불러온 값), 바꾼 값
- 처리: [예상 점수 계산하기]를 누르면 바꾼 값으로 다시 계산한다. N-17, N-21과 같은 구조를 쓴다.

- 입력: 바꾼 값 10개, 모델
- 처리: 바꾼 값을 모델 서버(FastAPI/LightGBM)에 넘겨 점수를 다시 구한다. 변화를 모형 재계산분과 대안 데이터 가점으로 나누고 등급 변화를 계산한다.

- ⚠️ 여기서 "대안 데이터 가점"은 대안 데이터 피처가 점수에 작용한 몫을 나눠 보여 주는 것이다. 삭제된 가산점(N-23)이 아니다. UI는 '금융 이력 영향'과 '대안 데이터 영향'으로 나눠 보여 준다.

- 출력: 감점 요인 3개(항목, 감점, 바꿀 조건, 최대 회복 점수)
- 테이블: assessment, assessment_factor, dim_feature

### N-20 DSR 계산기 · 재무 진단 · P1
연소득 대비 부채상환비율(DSR)을 계산한다. 직군마다 다른 것은 월 소득 입력뿐이다.

#### N-20-1 저장 데이터 조회 · P1
- 설명: 소득·대출·직군 값을 불러온다.
- 입력: 로그인 계정
- 처리: 회원의 값을 DB에서 조회한다.
- 출력: 월별 소득, 대출 원리금, 직군, 공과금 납부 상태(최근 12개월)
- 테이블: user_income_month, user_loan, app_user, user_utility_payment

#### N-20-2 직군별 추가 입력 항목 · P1
- 설명: 직군에 따라 월 소득 입력 방식만 다르게 받고, 그 밖의 데이터는 모든 직군에게 같게 받는다.
- 입력: 급여소득자: 월급(보너스 제외). 자영업자·프리랜서: 월별 소득(12개월). 그 밖의 입력(재직·운영·활동 기간, 대출, 자산, 지출 등)은 직군과 상관없이 같다.
- 처리: 직군에 맞는 월 소득 입력창을 보여 준다. 나머지 입력은 모든 직군이 같은 입력창을 쓴다.
- 출력: 직군별 월 소득 입력 화면
- 테이블: user_income_month
- 비고: N-05-2(직군별 소득 입력)와 같은 입력이다(11/12 팀 결정). 월평균 매출, 업종, 최근 소득 변동폭, 프로젝트 주기성, 공과금 납부율은 따로 입력받지 않는다. 소득 변동폭은 N-22-3에서 저장된 월별 소득으로 계산하고, 공과금 납부율은 모든 직군에게 N-20-5에서 보여 준다.
- ⚠️ UI: 재직·운영·활동 **기간**은 소득 입력(N-05-2)에서 받는다. 업종·공과금 납부율·프로젝트 주기성 입력은 UI에 없고, 11/12 결정으로 받지 않는다 → decisions.md D-24

#### N-20-3 연소득 집계 · P1
- 설명: 월별 입력값으로 연소득을 구한다.
- 입력: 월별 소득 또는 월급
- 처리: 자영업자·프리랜서는 월별 소득을 더하고, 급여소득자는 월급 × 12(보너스 제외)로 계산한다.
- 출력: 연소득
- 테이블: user_income_month
- 비고: 연소득 집계 기준 확정(10/30, 투표 D9).

#### N-20-4 DSR 계산·위험 단계 · P1
- 설명: 연간 원리금 상환액을 연소득으로 나눠 DSR을 구한다.
- 입력: 연 원리금, 연소득
- 처리: DSR = (연간 원리금 상환액 ÷ 연소득) × 100. 40%를 넘으면 위험 배지를 붙인다. 연소득이 0원이면 나눗셈 오류를 막고, BigDecimal로 반올림한다.
- 출력: DSR, 위험 단계
- 테이블: user_loan, user_income_month
- 비고: 상환 부담률(N-16-1)과 같은 계산이므로 함수를 공유한다. 모델 학습 후 결과에 따라 변경 예정.
- ⚠️ UI: **30% 이상 주의, 40% 이상 위험** 두 단계다(N-16-2와 같은 기준).

#### N-20-5 DSR 표시 · P1
- 설명: 비율과 위험 단계를 화면에 보여 준다.
- 입력: N-20-4 결과
- 처리: 비율과 위험 단계를 표시한다. 공과금 기한 내 납부율 = (12 − 미납 개월 수) ÷ 12를 참고 항목으로 함께 표시한다(데이터가 있는 달 기준, 12개월 미만이면 안내). DSR 계산에는 넣지 않는다.
- 출력: DSR, 위험 단계, 공과금 기한 내 납부율(참고, 모든 직군)
- 테이블: user_utility_payment

### N-21 소득·지출 변화 점수 예측 (전 현금흐름 시뮬레이터) · 재무 진단 · P1
월 소득이나 지출, 정기 납부 성실도가 바뀔 때 대안 점수가 어떻게 달라질지 예측한다.

#### N-21-1 저장 데이터 조회 · P1
- 설명: 현재 소득·지출·대출 값을 불러온다.
- 입력: 로그인 계정
- 처리: 현재 값을 DB에서 조회한다.
- 출력: 최근 월별 소득, 지출 항목, 대출 원리금, 간편결제, 최근 평가
- 테이블: user_income_month, user_expense_item, user_loan, user_easypay_usage, assessment

#### N-21-2 전망 조건 입력 · P1
- 설명: 소득·지출 변화와 예측 기간을 정한다.
- 입력: 월 소득 변동 폭, 월 고정 지출, 카드값·대출 납부(제때·밀림), 예측 기간(3·6·12개월)
- 처리: 바꿀 값을 입력받는다.
- 출력: 선택한 전망 조건
- 테이블: 없음

#### N-21-3 기타 지출 항목 관리 · P1
- 설명: 기타 지출 항목을 추가·삭제한다.
- 입력: 종류, 내용, 월 금액
- 처리: 기타 지출 항목을 추가·삭제한다.
- 출력: 기타 지출 목록
- 테이블: user_expense_item

#### N-21-4 공통 재계산 틀 · P1
- 설명: 바꾼 값으로 다시 계산하는 구조를 둔다.
- 입력: 현재 값, 바꾼 값
- 처리: 바꾼 조건으로 다시 계산한다. N-17, N-18과 같은 구조를 쓴다.
- 출력: 재계산 입력값
- 테이블: 없음

#### N-21-5 현금흐름 전망 계산 · P1
- 설명: 기간별 소득과 지출을 전망한다.
- 입력: 소득, 월 지출 합계, 월 원리금
- 처리: 기간별로 전망해 월 지출 합계, 월 원리금, 전망 순현금, 가장 나쁜 달을 계산한다. 간편결제 이용 내역은 지출 합계에 넣지 않는다.
- 출력: 월 지출 합계, 월 원리금, 전망 순현금, 가장 나쁜 달
- 테이블: user_income_month, user_asset_snapshot, user_expense_item

#### N-21-6 최근 12개월 적자 개월 수 계산 · P1
- 설명: 지출이 소득보다 큰 달을 센다.
- 입력: 최근 12개월 소득·지출
- 처리: 지출이 소득보다 큰 달의 수를 센다.
- 출력: 적자 개월 수
- 테이블: user_income_month, user_expense_item

#### N-21-7 성수기·비수기 소득 격차 계산 · P1
- 설명: 소득이 가장 높은 달과 낮은 달의 차이를 구한다.
- 입력: 월별 소득
- 처리: 소득이 가장 높은 달과 낮은 달의 차이를 계산한다.
- 출력: 성수기·비수기 소득 격차
- 테이블: user_income_month
- 비고: N-22-4와 같은 계산을 쓴다.

#### N-21-8 예상 대안 점수 재계산 · P1
- 설명: 바뀐 현금흐름으로 예상 대안 점수를 다시 구한다.
- 입력: 전망 값, 간편결제(비금융), 모델
- 처리: [예상 점수 계산하기]를 누르면 예상 대안 점수를 구한다. 간편결제는 점수 계산에 반영한다.
- 출력: 예상 대안 점수
- 테이블: user_easypay_usage, assessment
- 비고: 비금융 정보(통신·간편결제 등)가 바뀌는 경우는 N-18에서 다룬다.

#### N-21-9 실적·전망 차트 · P1
- 설명: 최근 12개월 실적 뒤에 전망을 이어 그린다.
- 입력: N-21-5~8 결과
- 처리: 최근 12개월 실적 막대 뒤에 예측 막대를 같은 색의 연한 색·점선으로 이어 그리고, '지난 12개월(실제) | 앞으로 n개월(예측)'을 표시한다. 월 지출선과 예상 점수선은 굵게 그리고 바탕색 테두리를 둘러 잘 보이게 한다.
- 출력: 실적·예측 막대(예측은 연한 색), 월 지출선, 예상 점수선(오른쪽 축), 예측 기간 누적 잉여, 가장 빠듯한 달, n개월 뒤 예상 점수
- 테이블: user_income_month

### N-22 소득 변동성 진단 · 재무 진단 · P0
월별 수입 편차를 보여 주고 비수기를 미리 경고한다. 프리랜서 대표 기능. 직군과 상관없이 모두에게 보인다(11/06).

#### N-22-1 저장 데이터 조회 · P0
- 설명: 최근 12개월 소득과 고정지출을 불러온다.
- 입력: 로그인 계정
- 처리: 회원의 값을 DB에서 조회한다.
- 출력: 최근 12개월 소득, 월 고정지출
- 테이블: user_income_month, user_asset_snapshot

#### N-22-3 변동성 지표 계산 · P0
- 설명: 최근 12개월 소득으로 변동성 지표를 구한다.
- 입력: 월별 소득, 월 고정지출
- 처리: 12개월 평균·중앙값, 가장 낮은 달 대비 고정지출, 소득 0원인 달 수, 최근 3개월 대비 12개월 평균을 계산한다.
- 출력: 변동성 지표
- 테이블: user_income_month, user_asset_snapshot
- ⚠️ UI는 월 소득 변동 계수 12% 초과를 "변동이 큼"으로 표시한다(시연용 예시, 설정 상수).

#### N-22-4 성수기·비수기 소득 격차 계산 · P0
- 설명: 소득이 가장 높은 달과 낮은 달의 차이를 구한다.
- 입력: 월별 소득
- 처리: 소득이 가장 높은 달과 낮은 달의 차이를 계산한다.
- 출력: 성수기·비수기 소득 격차
- 테이블: user_income_month
- 비고: N-21-7과 같은 계산을 쓴다.

#### N-22-5 소득 부족 달 확인 · P0
- 설명: 지난 12개월 중 소득이 월 고정지출보다 적었던 달을 찾는다.
- 입력: 최근 12개월 월별 소득(N-22-1 결과), 월 고정지출(N-22-3 결과)
- 처리:
  - 최근 12개월 중 소득이 월 고정지출보다 적은 달을 찾는다.
  - 그 달이 마지막 입력월 다음부터 몇 개월 뒤에 다시 오는지 계산한다.
  - 가장 가까운 달을 먼저 보여 주고, 그 달에 모자랐던 금액을 미리 모아 둘 금액으로 안내한다.
  - 부족한 달이 없으면 안내하지 않는다.
- 출력: 경고 여부, 부족했던 달 목록(월, 그 달 소득, 모자란 금액, 다시 오기까지 남은 개월 수), 가장 가까운 비수기와 준비 금액
- 테이블: user_income_month

#### N-22-6 월별 소득 차트·소득 부족 달 미리 알림 · P0
- 설명: 월별 소득을 차트로 보여 주고 소득 부족 달을 미리 알린다.
- 입력: N-22-2~5 결과
- 처리: 차트와 경고를 표시한다.
- 출력: 월별 소득 차트, 변동성 지표, 소득 부족 달 알림
- 테이블: user_income_month
- ⚠️ N-22-2는 삭제됐으므로 입력은 N-22-3~5 결과다(시트 표기는 "N-22-2~5").

### N-24 상권 분석 (차트·지도) · 재무 진단 · P1
서울 행정동별 상권 지표를 업종별로 보여 준다. 모든 직군이 서울 전체에서 시작한다(회원의 사업장 동·업종은 저장하지 않는다). 차트를 먼저 만들고 지도를 얹는다.

#### N-24-2 소상공인 상권 분석 (매출·점포 통계) · P1
- 설명: 서울시 상권 추정매출과 점포 데이터를 행정동·업종별로 조회한다.
- 입력: 행정동, 업종
- 처리: 같은 행정동·업종의 최근 4분기 매출, 점포 수, 폐업률을 조회한다. 비공개 칸은 "자료 없음"으로 표시한다.
- 출력: 매출, 점포 수, 폐업률
- 테이블: fact_dong_sales, fact_dong_store, dim_service_category

#### N-24-3 상권 분석 차트 · P1
- 설명: 매출 추세와 경쟁 밀집도를 차트로 보여 준다.
- 입력: N-24-2 결과
- 처리: 매출 추세와 경쟁 밀집도 요약을 차트로 그린다.
- 출력: 점포당 분기 매출, 폐업률, 매출 전년 대비 증감률, 4분기 매출 추이 차트, 경쟁 밀집도 요약
- 테이블: fact_dong_sales, fact_dong_store, dim_service_category

#### N-24-4 상권 공간 시각화 (지도 히트맵) · P2
- 설명: 행정동 경계 위에 매출과 폐업률을 색으로 보여 준다.
- 입력: 지표 선택(분기 폐업률·매출 전년비·개업률·점포 수 증감·유동인구 증감), 업종 선택(8개), 구 선택, 행정동 검색
- 처리: 지도 API와 행정동 GeoJSON 폴리곤으로 지도를 그리고, 매출 규모·폐업률에 따라 영역을 색칠한다. 동을 누르면 N-24-3 결과로 바뀐다.
- 출력: 상권 히트맵(기본 초록, 나쁨 선홍, 좋음 연청), 범례, 지도 아래 한 줄: 요약·구별 평균·행정동 분포·주의할 동/좋은 동
- 테이블: dim_adm_dong, fact_dong_sales, fact_dong_store, fact_dong_living_pop
- 비고: 지도 히트맵만 P2. 지도 API와 행정동 경계 데이터가 필요하다.
- ⚠️ 시트에는 "카카오맵 API"로 적혀 있지만, 11/06 확정 UI는 **네이버 지도 API**(자리 표시)다. UI를 따른다 → decisions.md

#### N-24-5 행정동 상세 창 · 미정
- 설명: 동을 누르면 그 동의 상세 현황과 업종 순위를 창으로 보여 준다.

- 설명: 미리 정한 질문 버튼을 누르면 설명을 보여 준다.
- 입력: 질문 버튼
- 처리: 미리 정한 질문 버튼 4개를 누르면 등록된 답을 보여 준다. 남은 질문 횟수는 줄지 않는다.
- 출력: 용어 설명
- 테이블: chatbot_preset_question
- 비고: 질문 버튼 방식으로 먼저 만든다.

#### N-32-2 자유 질문 AI 설명 · P2
- 설명: 사용자가 입력한 용어나 질문에 AI가 답한다.
- 입력: 금융 용어 또는 질문
- 처리: 직접 입력한 질문만 AI가 답하고, 하루 질문 횟수(10회)에서 차감한다. 무료 AI 한도에 맞춰 호출 횟수를 제한한다.
- 출력: 용어 설명, 남은 질문 횟수
- 테이블: chatbot_question_log, app_setting
- ⚠️ AI에 넘길 정보의 범위는 decisions.md D-21. 정해지기 전에는 사용자가 쓴 질문 글만 넘긴다.

### N-33 게시글·댓글 신고하기 · 커뮤니티 · P2
사용자가 부적절한 글이나 댓글을 신고한다. 게시판(N-06)을 만들 때 함께 구현한다.

#### N-33-1 신고 접수 · P2
- 설명: 게시글이나 댓글을 신고 사유와 함께 접수한다.
- 입력: 신고 대상(게시글 또는 댓글), 신고 사유(욕설·비방, 광고·스팸, 개인정보 노출, 허위 정보, 기타), 상세 내용(선택)
- 처리: 로그인한 사용자만 신고할 수 있다. 본인이 쓴 글은 신고할 수 없고, 같은 사용자가 같은 대상을 중복 신고할 수 없다. 신고를 접수 상태로 저장한다. 작성자가 아니라 글·댓글 자체를 신고한다. 한 사용자는 하루 3번까지 신고할 수 있다(설정값).
- 출력: 신고 접수 완료 안내. 본인 글, 중복 신고, 로그인 필요, 하루 신고 횟수 초과 시 오류 안내
- 테이블: content_report, board_post, board_comment, app_setting
- 비고: 접수된 신고는 관리자가 N-34에서 확인한다.

#### N-33-2 기준 건수 자동 숨김 · P2
- 설명: 신고가 기준 건수 이상 쌓이면 일반 사용자 화면에서 숨긴다.
- 입력: 대상별 누적 신고 건수
- 처리: 기준 건수 이상이면 대상을 자동으로 숨긴다.
- 출력: "신고로 숨김 처리된 글입니다" 표시
- 테이블: content_report, board_post, board_comment, board_post_log, app_setting
- 비고: 자동 숨김 후 관리자가 확인·관리하는 방식으로 확정(10/30, D-10).
- ⚠️ UI: 기준 **5건**, 집계는 **글·댓글 각각**(대상별), 관리자가 신고 접수 화면에서 **3~10건** 사이로 바꾼다(설정값). 세부 조정은 게시판 담당 팀이 정한다 → decisions.md

### N-34 신고 접수 게시판 (관리자 전용) · 관리자 · P2
관리자만 볼 수 있는 화면에서 접수된 신고를 확인하고 처리한다.

#### N-34-1 신고 목록·필터 · P2
- 설명: 관리자 역할을 확인한 뒤 신고를 묶어서 목록으로 보여 준다.
- 입력: 상태(접수, 검토 중, 처리 완료, 반려)·사유·기간 필터 / 자동 숨김 기준(건) 설정·저장, 미처리 건수 표시
- 처리: 관리자 역할인지 확인한 뒤에만 목록을 보여 준다. 같은 대상의 신고를 묶어 누적 건수와 사유별 건수를 계산하고, 자동 숨김된 대상을 먼저 보여 준다.
- 출력: 신고 목록(접수 시각, 대상 글, 사유, 누적 신고 건수, 상태)
- 테이블: content_report, board_post, board_comment, app_user
- 비고: 일반 사용자는 이 화면에 접근할 수 없다.

#### N-34-2 신고 상세 · P2
- 설명: 고른 신고의 원문과 사유별 건수를 본다.
- 입력: 처리할 신고 선택
- 처리: 원문과 사유별 건수를 조회하고 신고자는 마스킹해서 보여 준다.
- 출력: 신고 상세(원문, 작성자 닉네임, 사유별 건수, 마스킹된 신고자)
- 테이블: content_report, board_post, board_comment, app_user

#### N-34-3 처리 결과 저장 · P2
- 설명: 신고 처리 결과를 저장하고 게시판에 반영한다.
- 입력: 처리 결과(숨김 유지, 삭제, 반려), 처리 메모
- 처리: 처리자와 처리 시각을 남긴다. 숨김 유지나 삭제는 게시글·댓글에 반영하고, 반려는 숨김을 해제한다.
- 출력: 처리 결과 안내
- 테이블: content_report, board_post, board_comment, board_post_log
- 비고: 자동 숨김 후 관리자가 확인·관리하는 방식으로 확정(10/30, D-10).
- ⚠️ UI: 처리하면 신고자에게 결과를 알리고, 삭제한 경우에는 작성자에게도 알린다.

### N-35 개인신용정보 열람 감사 로그 · 관리자 · P1
관리자가 회원의 상세 신용·소비 데이터를 열람할 때 사유를 받고 접근 이력을 자동으로 기록한다.

#### N-35-1 열람 사유 입력·권한 검증 · P1
- 설명: 열람 전에 사유를 받고 권한을 확인한다.
- 입력: 대상 회원 ID, 열람자 ID, 열람 사유
- 처리: 열람 사유 입력 여부를 확인하고 권한을 검증한 뒤 열람을 허용한다. 사유가 없으면 열람을 막는다.
- 출력: 열람 결과
- 테이블: app_user, user_credit_profile, assessment, user_expense_item, user_easypay_usage, user_telecom_payment, user_utility_payment (확인 필요: user_social_insurance_payment 포함 여부)
- 비고: 원래 명세의 user·admin·credit_data·consumption_data는 DDL에서 app_user·user_credit_profile·assessment·user_expense_item·user_easypay_usage·user_telecom_payment·user_utility_payment로 정리했다. 통신비·공과금 납부 기록도 연체 여부가 드러나는 민감 정보라 열람 감사 대상에 넣었다(11/12).

#### N-35-2 감사 로그 자동 저장 · P1
- 설명: 열람 일시와 접근 정보를 자동으로 남긴다.
- 입력: N-35-1 결과
- 처리: 열람 일시와 접근 정보를 저장한다. 저장한 로그는 수정·삭제를 제한한다.
- 출력: 감사 로그 저장 결과
- 테이블: access_audit_log

### N-37 대출 상품 목록·상세·즐겨찾기 · 대출 상품 · 미정
시연용 더미 대출 상품을 모아 보고, 상세를 확인하고, 즐겨찾기한다. 주 메뉴 '대출 상품'으로 들어간다.

#### N-37-1 상품 목록·필터 · 미정
- 설명: 대출 상품을 카드로 모아 보고 조건으로 거른다.
- 입력: 필터(전체, 지금 점수로 가능, 내 직군 대상, 즐겨찾기)
- 처리: 더미 상품을 조건에 맞게 걸러 카드로 보여 준다. 내 대안 점수로 점수 조건을 채우는지 표시한다.
- 출력: 상품 카드(사업자 배너, 상품명, 한 줄 설명, 금리, 한도, 대상, 점수 조건 충족 여부, [상세 보기], [즐겨찾기])
- 테이블: loan_product, loan_product_worker_type, loan_product_favorite, assessment
- 비고: 배너 이미지가 없으면 사업자별 단색으로 채운다.
- ⚠️ UI: 시연용 더미 상품은 **9종**이고, "더미 상품 · 실제 상품 아님"을 표시한다.

#### N-37-2 상품 상세 · 미정
- 설명: 상품 하나의 조건과 설명, 내 점수 충족 여부를 본다.
- 입력: 상품 선택(목록, 시뮬레이터 추천 카드, 마이 페이지 즐겨찾기)
- 처리: 상품의 조건과 내 점수 충족 여부를 보여 준다. 시연에서는 [신청하기]를 누르면 안내만 한다.
- 출력: 배너(사업자명, 상품명, 설명), 금리·최대 한도·대출 기간·상환 방식, 상품 설명, 신청 조건과 특징, 필요 서류, 내 점수로 보면, 유의 사항, [즐겨찾기], [신청하기]
- 테이블: loan_product, loan_product_feature

#### N-37-3 상품 즐겨찾기 · 미정
- 설명: 마음에 드는 상품을 즐겨찾기에 넣고 뺀다.
- 입력: ☆ 즐겨찾기 버튼
- 처리: 상품을 즐겨찾기에 넣고 뺀다. 목록·상세·시뮬레이터 추천 카드에서 쓸 수 있다.
- 출력: 즐겨찾기 상태, 마이 페이지 즐겨찾기 목록(N-04-5)
- 테이블: loan_product_favorite
