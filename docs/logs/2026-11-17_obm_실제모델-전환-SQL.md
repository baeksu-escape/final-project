# 공용 DB 실제 모델 전환 준비 — 전환·되돌리기 SQL, 전환 절차, 모델 파일 해시 자동 대조

- **관련 결정:** 11/17 범영·재욱 합의(11/18 시연은 Mock 유지, 공용 DB ACTIVE 전환은 로컬 확인 후 DB 담당). PR #74(FP-141) 리뷰 지적 ②(모델 파일 없이 전환하면 전부 503)·④(해시 확인이 코드에 없음) 반영

## 무엇을, 왜 바꿨나
- FP-141(#74)로 FastAPI가 DB의 ACTIVE 모델 버전으로 계산기를 고르게 됐다. 공용 DB를 시연 이후 실제 모델로 바꾸기 위한 **전환 SQL·되돌리기 SQL·절차**를 만들었다. 이 PR을 병합해도 DB는 바뀌지 않는다(SQL은 DB 담당이 따로 실행).
- `activate_model_lgbm_base_0_1.sql`: FS-V1 모델 행·피처 38행이 있는지 먼저 확인하고(없으면 멈춤), 지금 ACTIVE를 RETIRED로 내린 뒤 `LGBM-BASE-0.1`을 ACTIVE로 올린다(ACTIVE는 한 행만 허용, `UX_MRG_ACTIVE`). 이미 ACTIVE면 그대로라 다시 실행해도 된다.
- `rollback_model_to_dev_dummy.sql`: 반대 방향 비상용. 저장된 평가는 지우지 않는다.
- FastAPI가 켜질 때 `artifacts/SHA256SUMS.txt`가 있으면 **joblib을 열기 전에 해시를 대조**하고, 다르면 열지 않고 준비 안 됨(실제 모델 요청 503). 목록 파일이 없으면 지금처럼 통과한다.
- DDL의 기본 ACTIVE(`DEV-DUMMY`)는 바꾸지 않았다. 새로 DB를 만드는 팀원 PC에는 모델 파일이 없을 수 있어 Mock이 안전하다. 그래서 DDL 체크리스트 대상이 아니다.

## 영향
- DB 변경 없음(전환 SQL은 파일만 추가). 공용 DB 실제 전환은 시연 이후 DB 담당이 절차대로 하고 팀에 알린다.
- 전환 뒤에는 공용 DB를 쓰는 모든 PC의 `fastapi_server/artifacts/`에 모델 파일 5개가 있어야 한다(없으면 503).

## 확인
- FastAPI `python -m unittest discover tests` **116개 통과**(새 2개)
- 받은 모델 묶음의 `SHA256SUMS.txt`를 `artifacts/`에 넣고 실제 로딩 → 준비됨(해시 일치)
- 로컬 연습 DB(공용 DB에는 실행 안 함) SQL 확인, 오류 없음
  - 전환 SQL을 이미 실제 모델인 DB에서 다시 실행 → "이미 LGBM-BASE-0.1이 ACTIVE" (바꾼 것 없음, 다시 실행해도 안전)
  - 되돌리기 SQL → `ACTIVE: LGBM-BASE-0.1 → DEV-DUMMY`
  - 전환 SQL → `LGBM-BASE-0.1` ACTIVE(ACTIVATED_AT 14:45:15), `DEV-DUMMY` RETIRED(되돌린 시각 14:44:37) — Mock → 실제 모델 방향 전환 확인
- 확인 못 함: 전환 SQL의 사전 확인(FS-V1이 없는 DB에서 멈춤)은 FS-V1이 이미 있는 DB뿐이라 직접 시험하지 못함(코드 검토로 대신)
