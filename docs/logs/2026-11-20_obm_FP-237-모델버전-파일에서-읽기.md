# 실제 모델 버전을 묶음 meta.json에서 읽기, LGBM-BASE-0.2 전환·되돌리기 SQL (1차)

- **날짜:** 2026-11-20
- **작성자:** 오범영 / Claude Code
- **브랜치:** `feature-B/FP-237-model-version-from-meta` (Jira FP-237)
- **관련 N-ID:** N-12-2 기존·대안 점수 계산·저장, N-18 신용케어 시뮬레이터
- **관련 결정:** 11/20 범영 (가)안 — 모델 버전은 코드 상수가 아니라 넣은 묶음 파일에서 정한다

## 무엇을, 왜 바꿨나
- 재욱 님이 단조 제약으로 재학습한 `LGBM-BASE-0.2`를 등록하려면, 원래는 코드 상수(`training/config.py` `MODEL_VERSION`)를 0.2로 바꿔야 했다.
- 그러면 그 코드가 develop에 들어가는 순간 0.1 묶음을 가진 모든 서버(공용 DB 서버 PC, 팀원 PC)가 실제 모델을 못 쓴다(점수 산출 MODEL_ERROR). 코드 병합·파일 교체·DB 전환을 같은 날 맞춰야 한다.
- 그래서 FastAPI가 **불러온 묶음의 meta.json(`model_version`)**을 실제 모델 버전으로 쓰게 했다. 0.1 묶음이면 0.1, 0.2 묶음이면 0.2로 동작하고, 모델 교체는 코드 없이 "파일 교체 + DB 등록·전환 SQL"로 끝난다(11/18 0.1 전환과 같은 방식).
- 0.2 등록 SQL은 0.2 묶음의 파일 해시가 필요해 2차 PR로 나눈다.

## DB·API 변경
- DB: 없음(새 SQL은 실행 전, 0.2 행이 없으면 전환 SQL이 멈춤)
- API: ML-01·02 `supportedModelVersions`가 "이 서버가 지금 계산할 수 있는 버전"으로 바뀜 — 묶음을 못 불러오면 `["DEV-DUMMY"]`만. Spring은 이 필드를 쓰지 않는다(코드 검색 확인)
- 영향을 받는 기능·팀원: 없음(0.1 묶음 서버는 그대로 0.1). 재욱 님 — 상수를 바꾸지 않아도 0.2 묶음이 0.2로 인식됨

## 확인
