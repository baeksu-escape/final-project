## 무엇을, 왜 바꿨나
- 재욱 님이 11/20에 단조 제약 8개로 다시 학습한 0.2 묶음(`avenue_model_files_20261120_v02.zip`)을 올렸다.
- 1차의 전환 SQL(`activate_model_lgbm_base_0_2.sql`)은 0.2 행과 모델 파일 기록 2행이 DB에 있어야 실행된다. 그 행들을 넣는 등록 SQL을 이번에 만든다.
- 등록만 하고 서비스는 바꾸지 않는다(0.2는 CANDIDATE). 켜는 것은 전환 SQL이 따로 한다.

## 바뀐 파일
| 파일 | 변경 내용 (1줄) |
|------|-----------------|
| `docs/spec/sql/register_model_lgbm_base_0_2.sql` | 새 파일. MODEL_REGISTRY 0.2(CANDIDATE, FS-V1) + MODEL_ARTIFACT 2행(파일 해시, seed 11 검증 AUC, METRICS_JSON). 학습 데이터는 0.1이 넣은 행을 그대로 가리킴. 사전 확인 2개, 다시 실행 안전 |

## 값의 출처
- 파일 해시: 묶음의 `SHA256SUMS.txt` 4줄을 직접 계산해 대조, 모두 일치
- 버전·피처 세트: 두 meta.json의 `model_version = LGBM-BASE-0.2`, `feature_set_version = FS-V1`
- 학습 데이터: 두 meta.json의 `data.table_sha256` 앞 8자리 `79511b5d` = 0.1과 같은 학습 표 → DATASET_VERSION 새 행 없음
- AUC_VALID: 서버에 올린 seed 11 모델 값(기존 0.6071 / 대안 0.6554). 두 모델은 라벨이 달라 나란히 비교하지 않는다

## DB·API 변경
- DB: 기준 데이터 행 추가만(MODEL_REGISTRY 1행, MODEL_ARTIFACT 2행). 테이블 구조는 그대로
- API: 없음
- 공용 DB: 아직 실행하지 않음. 팀이 0.2로 바꾸는 시점을 정하고, 그 DB를 쓰는 모든 PC가 0.2 묶음으로 바꾼 뒤 실행

## 확인 (로컬 DB·로컬 서버)
- 순서: 이 파일 → `artifacts/`를 0.2 묶음으로 교체 → `/v1/health` `modelVersion: LGBM-BASE-0.2` → `activate_model_lgbm_base_0_2.sql`
- 결과: 0.2 ACTIVE, 0.1 RETIRED. 등록 SQL을 한 번 더 실행해도 "이미 있음, 건너뜀"

## 실패한 두 계정 (이 PC 데이터 문제)
- demo_self: 통신비 또는 공과금 기관 기록이 비어 있어 점수 산출이 NOT_SCORABLE(ALT_DATA_EMPTY)로 끝난다. 설계대로다(피처 정의서 8-5).
  - 같은 이유로 DIAG-09 예상 점수가 400 `INVALID_INPUT`. FastAPI가 빈 기록을 422로 막고, Spring이 이것을 400으로 바꾼다.
  - 메시지가 "입력값을 확인해 주세요"뿐이라 원인을 알기 어렵다. 후속 개선 후보로 남긴다.
- demo_free: 입력 완료 현황에서 근무기간이 비어 있어 409 `INPUT_INCOMPLETE`. 평가가 없으니 뒤 단계가 모두 404다.
- 시연 계정 근무기간 시드는 회의에서 정하기로 했다(24/36/24).
