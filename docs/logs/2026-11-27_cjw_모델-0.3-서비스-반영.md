## DB·API 변경
- **DB:** 구조 변경 없음. 데이터만: 등급 구간 `CUT-0.4`, `SCORE_BAND_OFFER` 점수 구간, `LOAN_PRODUCT.MIN_ALT_SCORE`(727→712, 654→645), 모델 0.3 등록·평가 표본·같은 라벨 AUC.
- **기존 DB 실행 순서:** `add_cutoff_cut_0_4` → `register_model_lgbm_base_0_3` → `load_model_eval_sample_lgbm_base_0_3` → `update_model_metrics_same_label_lgbm_base_0_3` → 서버 파일 0.3 교체·health → `activate_model_lgbm_base_0_3` → `activate_cutoff_cut_0_4` → 0.3 시드 평가.
- **API:** 필드·경로 변경 없음. `cutoffVersion`·`gradeBands` 값이 모델 버전에 따라 달라진다.
- **영향:** 점수를 내는 PC는 0.3 묶음이 필요하다(DB ACTIVE가 0.3인 경우). 0.2 평가의 시뮬레이터는 "점수를 다시 산출" 안내가 난다. Mock(`DEV-DUMMY`)은 `CUT-0.3`으로 답하므로, 새 DDL로 만든 DB에서 Mock을 쓰면 평가 등급(CUT-0.3)과 금리·한도 참고 구간(CUT-0.4)이 다를 수 있다.

## 다음 사람이 알아야 할 것
- `load_seed_assessment_lgbm_base_0_3.sql`은 아직 없다. 로컬 전환 뒤 Spring 일괄 산출 → `export_seed_assessment.sql`로 만든다. **일괄 산출 도구(`--local.score-batch=true`)는 저장소에 없다**(0.2 시드는 11/24 범영 로컬에서 생성). 범영과 정해야 한다.
- 팀 공유가 필요하다: `avenue_model_files_20261127_v03.zip`(모델 4개 + `SHA256SUMS.txt`), `avenue_training_data_v3_7_0.zip`. 등록 SQL의 `FILE_URI`가 이 이름을 가리킨다.
- 남는 한계: 시드 회원의 불러온 신용 정보는 점수에 반영되지 않는다. 시연 계정 점수가 바뀐다.
- `demo_employee`: 0.2 시드 평가(904/753)에는 월 지출 60,000원이 들어 있는데 저장소 더미 시드는 1,461,547원이다. 저장소 시드로는 0.2 742/682, 0.3 717/714다(지출만 비교했을 때 시드 평가 318명 중 다른 회원은 이 1명). 0.3 시드 평가를 만들기 전에 산출 DB의 값을 범영과 확인한다.
- 발표 때 밝힐 것(평가 표본 기존 이력 3,000명 기준):
  - 리포트의 기존·대안 점수는 정답 라벨이 다른 모델의 점수다(평균 666.8 / 674.0, 좋음 11.6% / 25.2%). 기존 항목 모델도 라벨만 바꾸면 중앙값이 671 → 677이 되므로 점수 차이를 대안 데이터만의 효과로 설명하지 않는다.
  - 연체 라벨·컷오프 700에서 자영업자(대안 84.6% / 기존 81.8%)와 프리랜서(86.3% / 83.7%)는 대안의 우량 고객 오거절률이 더 높다.
  - 비금융 효과 라벨은 합성 데이터에 효과를 설계해 넣은 정답이라 대안 모델이 실제로 더 낫다는 근거가 아니다.
  - 시뮬레이터에서 대안 항목 하나만 바꿔도 "금융 이력 영향"이 0이 아닐 수 있다. SHAP 점수 변화를 항목 구분별로 더한 값이라 값이 그대로인 항목의 몫도 달라진다.
