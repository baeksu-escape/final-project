# 등급 상태 입력 부족(INSUFFICIENT_INPUT) 제거, 점수 범위·등급 경계 상수 (데이터 v3.5.12 / 더미 DB v2.4)

- **날짜:** 2026-11-09
- **작성자:** kgh / Claude Code
- **브랜치:** `KGH_Work`
- **관련 N-ID:** N-12(신용 리포트 등급 표시), N-05(데이터 입력 12개월)
- **관련 결정:** D-01(등급 경계 665·780 임시 확정), 11/09 결정(회원 월 입력 12개월 필수, 점수 범위 0~1000)

## 무엇을, 왜 바꿨나
- 회원 월 입력 12개월이 필수가 되어, 덜 차면 점수 산출 요청 자체를 막는다. 그래서 등급 상태 `INSUFFICIENT_INPUT`을 없애고 `SCORED`·`NOT_SCORABLE` 두 개만 둔다.
- 서비스 점수 0~1000, 등급 경계 665·780(Caution 0~664 / Standard 665~779 / Good 780~1000)을 `build_db.py` 상수 한 곳에 두었다. 범위는 `SCORE` CHECK로 걸고, 경계는 모형 학습 후 바뀔 수 있어 코멘트에만 적었다(CHECK 없음).
- 데이터 패키지는 문서만 바뀌어 v3.5.12(문서만), DB 묶음은 v2.4.

## DB·API 변경
- DB: `MEMBER_CREDIT_GRADE`만 바뀜. 컬럼 이름·타입 그대로. CHECK `CK_MCG_GRADE_STATUS_CODE` 허용값에서 `INSUFFICIENT_INPUT` 삭제, CHECK `CK_MCG_SCORE`(`SCORE BETWEEN 0 AND 1000`) 추가, 테이블·컬럼 코멘트 4개. 시드 없는 테이블이라 데이터 변화 없음.
- API: 없음(API 초안의 409 `INPUT_INCOMPLETE`가 입력 부족을 대신한다)
- 영향을 받는 기능·팀원
  - 백엔드 등급 산정: `INSUFFICIENT_INPUT`을 쓰지 않는다. 등급 경계 665·780은 Spring 쪽에도 설정 상수 한 곳이 필요하다(DB는 경계를 검사하지 않음).
  - 이미 v2.3을 적재한 개발 DB는 `run_all.sql`로 다시 만든다.

## 다음 사람이 알아야 할 것
- ⚠️ `docs/ai/decisions.md:75`는 점수 범위를 **300~900**으로 적고 있다(경계 665·780은 같음). 11/09 결정(0~1000)으로 문서 담당자가 고칠지 확인 필요. 이번 작업에서는 고치지 않았다.
- 경계를 바꾸려면 `build_db.py`의 `GRADE_STANDARD_MIN`·`GRADE_GOOD_MIN`을 고치고 다시 생성한다(코멘트만 바뀜). Spring 상수도 함께 바꾼다.
- `SCORE` 타입은 `NUMBER(12,6)` 그대로다. API 초안은 정수 점수라 타입을 줄일지는 DDL 확정 때 정한다.
- 과거 이력(CHANGES.md v3.5.7·v3.5.11 항목, DB README 「v2.2 → v2.3 변경」, 11/05 로그)의 `INSUFFICIENT_INPUT` 언급은 이력이라 그대로 두었다.
- 학습 전달 묶음은 v3.5.12로 다시 만들었다(`avenue_training_data_v3_5_12.zip`, 팀 공유 드라이브 업로드는 사용자가 한다). `fastapi_server/data/README.md`의 버전 표도 v3.5.12로 고쳤다(위 「바뀐 파일」 참고).
- `verify_statistics` 실패 원인은 줄바꿈이다. 저장소의 `reference/statistics/*.csv` 2개가 체크아웃 때 CRLF로 바뀌어 `statistical_priors.json`에 기록된 SHA256(LF 기준)과 달라진다. LF로 바꿔 계산하면 두 파일 모두 기록과 같다. `.gitattributes`로 이 CSV들을 바이너리(`-text`) 처리할지 정해야 한다(공통 설정이라 이번에 고치지 않음).
