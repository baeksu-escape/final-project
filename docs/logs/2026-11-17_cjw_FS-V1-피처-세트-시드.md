# 피처 세트 FS-V1(DRAFT)과 모델 버전 LGBM-BASE-0.1(CANDIDATE) 추가

- **날짜:** 2026-11-17
- **작성자:** 최재욱(B팀 모델·정의서 담당) / Claude Code
- **브랜치:** `feature-B/FP-135-fs-v1-seed` (Jira 키는 모델 버전 항목이 속한 FP-135로 가정, 다르면 알려 주세요)
- **관련 N-ID:** N-12-2, N-12-6(모델별 피처 칩), N-14
- **관련 결정:** 정의서 10장 C9(피처 38개)·C23, O-17(첫 점수 저장 전 FS-DRAFT → FS-V1), 11/17 범영·재욱 합의(FS-V1은 새 세트로 추가·상태 DRAFT·38개 고정(바뀌면 FS-V2)·모델 버전 `LGBM-BASE-0.1`을 두 모델 한 묶음으로)

## 무엇을, 왜 바꿨나
- 실제 학습 모델의 피처는 38개(`LRZ021201` 제외)인데 DB 피처 세트는 FS-DRAFT 39개뿐이라 SHAP 38개와 리포트 칩 개수가 어긋난다. 11/16 로그에 "FS-V1 시드는 재욱이 추가"로 되어 있어 새 피처 세트 `FS-V1`(상태 DRAFT)과 모델 버전 `LGBM-BASE-0.1`을 추가했다.
- **서비스는 바뀌지 않는다.** `MODEL_REGISTRY`의 새 행은 CANDIDATE이고 DEV-DUMMY가 ACTIVE 그대로다. ACTIVE 전환(DEV-DUMMY → RETIRED)과 공용 DB 적용은 범영 님이 따로 한다(11/18 1차 공유는 Mock 그대로).
- 방식은 ALT_DATA_EMPTY(PR #60)와 같다: 기준 데이터 2행은 `avenue_ddl.sql`에, 피처 38행은 FS-DRAFT 시드를 고치지 않고 새 파일 `seed/avenue_seed_dim_feature_fs_v1.sql`에 넣었다(값의 원본은 정의서 11장).
- 학습 코드에 `MODEL_VERSION`·`FEATURE_SET_VERSION`·`ALGORITHM_NAME` 상수를 두고 설명 파일(`*.meta.json`)에 기록하게 했다(FP-135 "모델 버전" 항목). 시험이 DB 기준 데이터와 같은 값인지 검사한다.

## DB·API 변경
- DB: 기준 데이터 변경만 있고 테이블·열·제약 변경은 없다. `FEATURE_SET_VERSION`에 FS-V1(DRAFT) 1행, `MODEL_REGISTRY`에 LGBM-BASE-0.1(LightGBM, FS-V1, CANDIDATE, `TRAINED_AT` 2026-11-16 11:19:49 UTC) 1행, `DIM_FEATURE`에 FS-V1 38행.
- API: 없음. 다만 범영 님 RPT-02·03 `modelFeatures`가 `DIM_FEATURE`를 읽으므로 FS-V1로 점수를 저장하기 시작하면 칩이 18/38개로 나온다(코드 수정 없음).
- 영향을 받는 기능·팀원: 범영 님(공용 DB 적용·ACTIVE 전환·FP-141), 경환 님(더미 DB 생성기 `build_db.py`·시험 변경 확인), 이미 DB를 만든 팀원(변경 SQL 1회 + 시드 1회).

## 확인
- 확인함: FastAPI 테스트 104개 통과(기존 93 + 새 11). DB 생성 도구 테스트 52개 통과(건너뜀 3개, `cryptography`·`pandas`·`bcrypt`를 임시 가상환경에 설치해 실행, 저장소 변경 없음). `avenue_ddl.sql`과 사본, 시드와 26번 사본이 바이트까지 같고 `seed_report.json`의 DDL 지문(LF 정규화)이 새 DDL과 일치. 시드 38행은 정의서 11장·학습 피처 목록과 같고 FS-DRAFT 시드와의 차이는 `LRZ021201` 제거와 순서 재번호뿐. `python -m training.train`을 임시 폴더로 실행해 AUC(기존 0.6049 ± 0.0026, 대안 0.6533 ± 0.0051)와 `.joblib` SHA-256이 공유본과 같고 설명 파일에 새 필드가 들어감.
- 확인 못 함: **Oracle에서 시드·변경 SQL을 실행하지 못했다**(로컬 DB에서 사용자가 확인 예정: 변경 SQL 두 번 실행해도 중복 없음 → 시드 실행 → FS-V1 38행·`LGBM-BASE-0.1` CANDIDATE·DEV-DUMMY ACTIVE 유지). 새 스키마에서 `avenue_ddl.sql` 전체 실행, 공용 DB 적용, 생성기를 팀 키로 다시 돌려 묶음을 만드는 것은 하지 않았다.

## 다음 사람이 알아야 할 것
- 설명 파일은 이 PR이 병합된 뒤에 다시 만들어 공유한다. 이때 `trained_at`은 새로 학습한 시각이 아니라 원래 파일의 값(2026-11-16T11:19:49)을 유지해야 DB의 `TRAINED_AT`과 맞는다(`.joblib`은 바이트까지 같다).
- FS-V1 상태 DRAFT는 정의서가 확정되면 CONFIRMED로 바꾸고, 실제 모델이 점수 저장을 시작한 뒤에는 38개 목록이 고정이다(바뀌면 FS-V2).
- 시드는 정확히 한 번만 실행한다(다시 실행하면 PK 중복). 삭제 안전장치는 `ASSESSMENT_FACTOR`가 코드를 FK로 가리킬 수 있어 일부러 두지 않았다.
- `MODEL_ARTIFACT`·`DATASET_VERSION` 장부 등록은 이번 범위가 아니다.
- 로그 파일명의 작성자 약어 `cjw`는 제안이다.
