## 무엇을, 왜 바꿨나
- FP-143 세 항목을 진행했다: ① 화면 → Spring → FastAPI → DB 저장 E2E 검증 ② 평가 조회 쿼리 실행 계획·인덱스 점검 ③ 예외 처리·로그 보강.
- ① 매번 손으로 누르지 않도록 화면이 부르는 API를 같은 순서로 부르는 자동 점검 스크립트를 만들었다(파이썬 기본 라이브러리만).
- ③ 11/18 공용 DB 점수 산출이 409로 거절됐을 때 서버 로그에 아무것도 없어 원인을 DB 조회로 찾아야 했다. 업무 오류도 상태·코드·경로를 한 줄 남기게 했다.
- 11/19 병합된 PR(#99·#101·#103·#106)과 광희·경환 님 요청을 API 정의서에 반영했다.

## 확인
- **E2E 자동 점검(로컬 DB, `LGBM-BASE-0.1`, demo_employee): PASS 15 / FAIL 0.** 실제 모델·SHAP 38개·피처 칩 18/38, 같은 requestId 재요청 시 같은 결과, 시뮬레이터·예상 점수는 진단 내역을 늘리지 않음
- **실행 계획(로컬 DB, ASSESSMENT 22행·ASSESSMENT_FACTOR 763행):** requestId 조회 `INDEX UNIQUE SCAN`(UK_ASM_REQUEST_ID), SHAP 요인 `INDEX RANGE SCAN`(UK_ASF_RANK). 최신 평가·진단 내역·점수 보유 여부는 22행이라 `TABLE ACCESS FULL`(정상). 통계를 10만 행·회원 1만 명으로 가정하면 최신 평가 쿼리가 `INDEX RANGE SCAN`(IX_ASM_USER_ASSESSED)으로 바뀜 → **인덱스 추가 불필요.** N-25 표본은 별도 표라 `ASSESSMENT`에는 서비스 회원 평가만 쌓임
- **백엔드 전체 테스트 395개 통과**(`./mvnw clean test`, 3차 리뷰 반영 후. 처음 392개 + 경로 변수 로그 테스트 1개 + 원인 체인 테스트 2개). 3차 반영 후 E2E도 demo_employee PASS 16 / FAIL 0 새 로그 예: `API 오류 404 PRODUCT_NOT_FOUND POST /api/members/me/__test/items/{code}/conflict`(경로 변수 값 대신 템플릿), `처리하지 못한 오류: java.lang.IllegalStateException at SecurityTestController.boom:… (POST …)`
- **검수 반영 후 E2E(로컬 DB, 0.2, 기대 버전은 health에서 읽음): demo_employee PASS 16 / FAIL 0.** E2E-09B(다른 회원 평가 → 404)는 세 계정 모두 PASS. demo_self(통신비·공과금 기록 비어 NOT_SCORABLE)·demo_free(근무기간 비어 409)는 로컬 계정 데이터 문제로 실패
- E2E 스크립트 새 검사 함수(E2E-11·13)는 정상·틀린 응답 예시로 따로 확인함(틀린 점수 차이·다른 출발 평가를 잡아냄)
- 정의서·명세서 상대 링크 41개 검사 → 깨진 링크 0
- 수동 점검 M-01~06은 병합 후 따로 했다(아래 「수동 점검 결과」, FP-238에서 추가)

## 점검 중 발견한 것
- 로컬 DB의 `demo_employee` 월급이 **24,046,340원(오타)**이라 예상 점수가 크게 틀어졌다 → 화면에서 2,404,634원으로 고침. 공용 DB 시연 계정도 같은 오타가 있는지 확인 필요.
- 고친 뒤에도 모델 방향이 상식과 다른 작은 사례가 남음(지출 2배 +11점, 카드 사용률 95%가 10%보다 높음, 카드 정보 없음이 가장 낮음). 연동 문제가 아니라 모델 학습 방향 문제 → 재욱 님께 사례 표 전달, 단조 제약(monotone_constraints) 시험 후 `LGBM-BASE-0.2` 채택 여부 결정(11/27 전).

## 다음 사람이 알아야 할 것
- E2E는 점수 산출(E2E-03)이 평가 1행을 실제로 저장한다. 평소엔 로컬 DB로 돌린다.
- 기대 모델 버전은 FastAPI health에서 읽으므로 모델을 바꿔도 스크립트를 고치지 않는다. 서버 묶음과 DB ACTIVE가 어긋나면 E2E-03(MODEL_ERROR)·05·13에서 드러난다.
- E2E-11·13은 "가장 최근 평가가 SCORED"를 전제로 리포트 점수와 비교한다. 최근 평가가 NOT_SCORABLE인 계정은 E2E-03과 함께 실패한다(시뮬레이터는 그 전의 SCORED 평가에서 출발하므로).
