- **관련 결정:** 11/17 범영·재욱 합의 — 모델 버전 `LGBM-BASE-0.1`(두 모델 한 묶음), 피처 세트 `FS-V1`(38개, 재욱 시드 PR), 모델 파일이 없으면 503 `MODEL_NOT_READY`(Mock 자동 대체 안 함), 11/18 시연은 Mock 유지·공용 DB ACTIVE 전환은 로컬 확인 후 범영

## 무엇을, 왜 바꿨나
- ML-03·ML-04가 **요청에 들어온 모델 버전으로 계산기를 고른다.** `DEV-DUMMY`(또는 버전 없음) → 지금 Mock, `LGBM-BASE-0.1` → 실제 모델, 그 밖 → 409.
  - Spring은 DB의 ACTIVE 모델 버전을 보내므로 **DB 전환이 곧 스위치**다. 이 변경을 병합해도 DB가 `DEV-DUMMY`인 동안은 동작이 그대로다(시연 안전). FastAPI가 무조건 실제 모델로 바뀌면 병합 순간 모든 DB에서 409 → `MODEL_ERROR`가 나기 때문에 이렇게 했다.
  - 응답의 `modelVersion`·`featureSetVersion`도 고른 계산기를 따른다(Mock `FS-DRAFT`, 실제 `FS-V1`). Spring은 응답 값으로 저장하므로 Spring 수정은 없다.
- 실제 모델 계산(`pipeline/model_scorer.py`): 서버가 켜질 때 `artifacts/legacy.joblib`·`alternative.joblib`을 한 번 불러온다. 대안 점수·SHAP은 재욱 `training/explain.py`(`AlternativeExplainer.explain`), 기존 점수는 `score_one(..., "legacy")`, 등급은 기존 CUT-0.1. 응답 모양은 Mock과 같다.
  - 파일이 없거나, 설명 파일(`meta.json`)에 적힌 모델 버전·피처 세트가 서비스 값과 다르거나, 불러오기에 실패하면 "준비 안 됨" → health `modelLoaded: false`, `LGBM-BASE-0.1` 요청 503.
- ML-04 시뮬레이터도 저장된 평가의 모델 버전으로 계산기를 고른다(감점 요인 3개·회복 점수 포함).
- 피처 계산의 소수 반올림을 학습 생성 코드와 같은 ROUND_HALF_UP으로 맞췄다(`TODO(FP-141)` 해결).
- 서버 코드가 `training/`을 불러오게 되어 Dockerfile(2차 후보)에도 `training/` 복사 한 줄을 넣었다.

## 영향
- API 동작: ML-01 응답에 `supportedModelVersions` 추가, `modelLoaded`가 실제 모델 로드 여부를 뜻하게 바뀜. ML-02 응답에 `supportedModelVersions` 추가. ML-03·ML-04는 `LGBM-BASE-0.1` 요청을 받을 수 있게 됨(그 밖 동작은 그대로).
- DB 변경 없음. 실제 모델 점수를 저장하려면 재욱 님 FS-V1 시드(`FEATURE_SET_VERSION` FS-V1, `DIM_FEATURE` 38행, `MODEL_REGISTRY` `LGBM-BASE-0.1` CANDIDATE)가 먼저 들어와야 한다.
- 다음 순서: 재욱 FS-V1 시드 PR 병합(경환 생성기 확인) → 새 `meta.json` 묶음 교체 → 범영 로컬 DB에서 ACTIVE 전환 SQL로 실제 점수 확인 → 시연 이후 공용 DB ACTIVE 전환(전환 SQL은 그때 별도 파일).
