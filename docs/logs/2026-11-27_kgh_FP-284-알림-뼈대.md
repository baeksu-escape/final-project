## 다음 사람이 알아야 할 것

### 1. 로그인 확인 — 현재 구조
- JWT는 `Authorization: Bearer` 헤더로만 받는다(`JwtAuthenticationFilter`). 프론트는 토큰을 `localStorage`(`avenue.accessToken`)에 두고 `client.js`의 `fetch`가 헤더를 붙인다. **쿠키는 쓰지 않는다** — 세션 없음(STATELESS), CSRF 끔, CORS는 `allowedHeaders`에 `Authorization`만 있고 `allowCredentials`가 없다(`SecurityConfig` 주석에도 "쿠키(credentials)는 쓰지 않는다").
- 브라우저 `EventSource`는 헤더를 붙일 수 없다. 그래서 쿠키로 바꾸려면 로그인·CORS·CSRF 전체를 건드려야 해서 이번 범위가 아니다.
- 대안 A(추천): **`fetch`로 스트림을 직접 읽는다.** `fetch(url, { headers: { Authorization } })`의 `response.body.getReader()`로 `text/event-stream`을 읽고 줄을 나눠 해석한다. 기존 토큰·필터·CORS를 그대로 쓰므로 **Security 설정 변경 0줄**, 서버는 보통의 SSE 응답이다. 단점은 자동 재연결이 없어 프론트가 직접 재연결 코드를 쓴다는 점(라이브러리 `@microsoft/fetch-event-source`를 쓰면 줄지만 새 라이브러리라 사전 확인이 필요하다).
- 대안 B: 일회용 티켓. `POST /api/members/me/notifications/stream-ticket`(헤더 인증)이 짧은 랜덤 티켓(예: 30초, 1회 사용, 서버 메모리)을 주고, `GET .../stream?ticket=…`이 티켓으로 인증한다. `EventSource`를 쓸 수 있어 재연결이 자동이다. 대신 스트림 경로를 `permitAll`로 열고 티켓 검증을 따로 만들어야 하며, 주소에 값이 남으므로 보안 주의가 필요하다(아래).
- 하면 안 되는 것: 액세스 JWT를 `?token=`으로 그대로 넣기. 주소는 접근 로그·브라우저 기록·프록시 로그에 남고, 토큰 유효 시간이 60분이라 유출 피해가 크다. 티켓 방식이라도 티켓은 짧게(수십 초)·1회용으로, 로그에는 마스킹한다.
- 결론: **A로 시작**, 재연결이 번거로우면 B를 후속으로. (팀 결정 필요 항목: 새 라이브러리 사용 여부는 A를 라이브러리로 할 때만.)

### 2. Security 설정 변경
- A 방식: `SecurityConfig.java` **변경 없음**. `/api/members/me/notifications/**`는 기존 `/api/members/me/**` 규칙(`hasRole("USER")`)에 이미 걸린다. 관리자는 403(다른 `me` API와 같음).
- B 방식: `SecurityConfig.java`에 스트림 경로 `permitAll` 1줄(`auth.requestMatchers(HttpMethod.GET, "/api/members/me/notifications/stream").permitAll();`을 `/api/members/me/**` 규칙 **앞**에 추가), 티켓 발급 POST는 기존 규칙으로 인증, 티켓 검증은 컨트롤러·서비스에서. 공유 파일이라 고치기 전에 확인이 필요하다(AGENTS.md 3-1).
- 둘 다 CORS는 `Accept: text/event-stream` 요청을 허용해야 한다. `allowedHeaders`에 `Accept`는 이미 있다. 스트림 응답은 연결 시 한 번만 검사하므로 별도 변경은 없다.
- 로그인 풀림: 액세스 토큰은 60분(`avenue.auth.jwt.expires-minutes=60`)이다. 연결 중에는 필터가 다시 실행되지 않으므로, **서버가 토큰 만료 시각에 맞춰 연결을 닫거나** 하트비트 때 계정 상태를 확인하는 방법이 필요하다. 프론트는 연결이 끊긴 뒤 재연결하다가 401을 받으면 기존처럼 로그아웃(`UNAUTHORIZED_EVENT`)시킨다.

### 3. Spring SseEmitter
- 컨트롤러: `GET /api/members/me/notifications/stream`, `produces = text/event-stream`, 반환 `SseEmitter`. 현재 회원 번호는 `AuthUser`에서 받는다(URL에 회원 번호를 넣지 않는 규칙).
- 타임아웃: 값을 직접 정한다(예: 30분 또는 토큰 남은 시간 중 짧은 쪽). 기본값은 서버 설정에 따라 짧을 수 있어 `new SseEmitter(ms)`로 명시한다. 끝나면 프론트가 재연결한다.
- 하트비트: 20~30초마다 `: ping` 주석 이벤트(또는 `event: ping`)를 보낸다. 프록시·공유기의 유휴 연결 끊김을 막고, 보내다 실패하면 끊긴 연결을 정리하는 계기가 된다.
- 회원별 여러 탭: `Map<Long, CopyOnWriteArrayList<SseEmitter>>`처럼 **회원 한 명에 연결 여러 개**를 둔다. 알림이 생기면 그 회원의 모든 연결에 보낸다. `onCompletion`·`onTimeout`·`onError`에서 목록에서 제거하고, 보내다 `IOException`이 나면 그 연결만 제거한다. 탭이 많은 회원을 막기 위해 회원당 상한(예: 5개)을 두고 넘으면 가장 오래된 연결을 닫는 것을 권한다.
- 서버가 한 대라는 전제(메모리 보관)다. 서버를 여러 대로 늘리면 Redis pub/sub 같은 공유가 필요하지만 이번 범위가 아니다.
- 알림 생성과 발송 순서: ①`USER_NOTIFICATION` INSERT(트랜잭션) ②커밋 뒤에 emitter로 전송(`@TransactionalEventListener(AFTER_COMMIT)` 권장 — 롤백된 알림이 화면에 뜨지 않게). 전송 실패는 저장된 알림에 영향을 주지 않는다.
- 이벤트 내용은 최소로: `id`(NOTIFICATION_ID), `type`, `title`, `linkUrl`, `createdAt`. **제목·내용에 개인정보 원문 금지**, `LINK_URL`은 서비스 내부 경로만(`/`로 시작, `//`·`http` 금지)이며 저장 전에 서버가 검사한다.
- 스레드: 서블릿 스레드를 오래 잡지 않도록 `SseEmitter`는 비동기로 동작한다. 하트비트용 스케줄러는 기존에 쓰는 것이 있는지 확인하고 없으면 `@Scheduled`(`@EnableScheduling` 필요 — 공통 설정 변경이라 확인) 또는 전용 `ScheduledExecutorService`를 쓴다.
- 비동기 요청은 Spring Security가 요청을 다시 검사(ASYNC dispatch)한다. 원 요청에 헤더가 그대로 있어 A 방식은 문제 없고, 구현 후 `SecurityConfigTest`처럼 401·403·200을 확인한다.

### 4. 프록시·배포 설정 (저장소 확인 결과)
- `frontend/vite.config.js`는 `plugins: [react()]`뿐이고 **개발 프록시가 없다.** 프론트는 `VITE_API_BASE_URL`(예: `http://localhost:8080`)로 백엔드를 **직접** 부르고 CORS(`avenue.cors.allowed-origins`)로 허용한다. 개발 중에는 중간 버퍼가 없어 SSE가 그대로 흐른다.
- 저장소에 nginx·docker-compose 등 **배포용 프록시 설정은 없다**(`fastapi_server/Dockerfile`만 있음). 배포 때 nginx 등을 앞에 두면 SSE 경로에 다음을 넣어야 한다: 버퍼링 끔(`proxy_buffering off`, 또는 응답에 `X-Accel-Buffering: no` 헤더를 서버가 보냄), 읽기 시간 제한을 하트비트 간격보다 크게(`proxy_read_timeout` 수 분 이상), HTTP/1.1 유지. 응답 압축(gzip)을 SSE 경로에는 쓰지 않는다.
- 브라우저는 같은 서버로 HTTP/1.1 연결을 6개까지만 열 수 있어, 탭마다 연결이 하나 늘면 그 탭의 다른 요청이 막힐 수 있다(HTTP/2에서는 해소). 그래서 회원당 연결 상한이 필요하다.
- 응답 헤더: `Content-Type: text/event-stream`, `Cache-Control: no-cache`.

### 5. 끊김과 놓친 알림
- 연결은 언제든 끊긴다(타임아웃·네트워크·서버 재시작). **알림의 진실은 DB**이고 SSE는 "새로 생겼다"는 신호다.
- 프론트: ①화면이 열리면 목록 `GET`을 먼저 불러오고 ②스트림을 연결한다. ③연결이 끊기면 몇 초 뒤 재연결(백오프: 1·2·4…최대 30초)하고, **다시 연결되면 목록을 다시 불러온다**(끊긴 사이 놓친 알림 보충). ④탭이 다시 보일 때(`visibilitychange`)도 한 번 불러온다. 401이면 재연결하지 않고 로그아웃 처리한다.
- 서버의 `Last-Event-ID` 재전송은 만들지 않는다(목록 다시 불러오기로 충분하고 서버 상태가 없어진다). 이벤트 `id`는 NOTIFICATION_ID로 두어 프론트가 이미 있는 알림은 중복으로 넣지 않게 한다.
- 안 읽은 개수는 목록 응답의 `unreadCount`로 내려 헤더 배지의 기준으로 삼는다(스트림은 신호 역할만).
- mock 모드(`VITE_USE_MOCK`)에서는 SSE를 흉내 내지 않고, 목록·읽음만 mock으로 하고 스트림은 연결하지 않는 것을 제안한다.
