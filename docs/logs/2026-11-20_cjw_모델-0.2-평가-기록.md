# 모델 0.2(단조 제약 후보 B) 학습 옵션과 평가 표본·같은 라벨 AUC 기록 SQL

- **날짜:** 2026-11-20
- **작성자:** 최재욱(B팀 모델·정의서 담당) / Claude Code
- **브랜치:** `feature-B/FP-136-model-0-2` (Jira FP-136, 키는 확정되면 맞춘다)
- **관련 N-ID:** N-12-2(점수 모델 학습), N-25(모형 성능 비교)
- **관련 결정:** 정의서 10장 C25(모델 0.2)·C26(TEST 사전 기준), 9장 결측 처리 행, `decisions.md` D-31(미정), 11/20 범영 E2E 점검과 11/20 재욱 결정(후보 B 채택, 씬파일 학습 c안은 쓰지 않음), 11/19 DDL·공용 md는 재욱 작업과 연계되면 직접 수정 가능

## 무엇을, 왜 바꿨나
- 범영 님 E2E 점검(11/20)에서 `LGBM-BASE-0.1`이 상식과 반대로 움직이는 사례가 나왔다(소득 +50% -8, 지출 2배 +11, 고정지출 300만 +9, 카드 95%가 10%보다 높음). 방향이 분명한 8개 피처에 LightGBM 단조 제약을 걸어 다시 학습한 모델이 `LGBM-BASE-0.2`다(후보 B). 학습 데이터(기존 집단 TRAIN 8,400행)와 피처 세트(`FS-V1` 38개)는 0.1과 같다.
- 학습 옵션을 코드에 추가했다. 옵션 없이 실행하면 0.1과 같은 결과이고(서버 모델 파일과 VALID 예측 차이 0.0, VALID AUC 0.6049·0.6533 재현), `--monotone`을 켜면 0.2가 된다. `--with-thinfile`(씬파일 노출 1 TRAIN을 학습에 더함)도 만들어 시험했으나 신용 이력 없음의 점수가 크게 내려가고 기존 모델에 새 이상이 생겨 쓰지 않았다(옵션만 남김, 기본 꺼짐).
- 0.2의 평가 표본 적재 SQL과 같은 라벨 AUC 갱신 SQL을 만들었다. 0.2 등록은 DB 담당(범영)이 하므로, 이 SQL은 등록 뒤에 적용한다.
- 정의서에 0.2 기록(C25)과 FP-144 TEST 평가 사전 기준(C26)을 남겼다. 기준은 TEST를 보기 전에 정했다(결과를 본 뒤 바꾸지 않았다는 증거).

## 확인
- 확인함: FastAPI 테스트 179개 통과(새 시험 포함), DB 도구 테스트 52개 통과(건너뜀 3). 옵션 없는 학습이 서버 모델과 같은 예측을 냄. 0.2 학습 결과 VALID AUC 기존 0.6047±0.0043, 대안 0.6591±0.0054(시드 5개). 적재 SQL 3,085행, 서버 모델 재현 확인 "같음", 갱신 SQL의 숫자는 `compare_labels --monotone` 결과와 같음. 0.2 모델 묶음은 서비스 로더에서 버전 상수를 0.2로 맞췄을 때 `ready=True`(임시로 상수를 바꿔 확인, 저장소는 그대로).
- 로컬 Oracle(SQL Developer, 11/20 사용자 확인): 0.1 등록 SQL → 0.2 등록 SQL(PR #113, 두 번 실행해 두 번째는 세 줄 모두 "이미 있음, 건너뜀") → 이 PR의 적재 SQL(정상 통과) → 갱신 SQL 순서로 실행했다. `MODEL_REGISTRY`는 `DEV-DUMMY` ACTIVE, 0.1·0.2 CANDIDATE, 갱신 뒤 `MODEL_ARTIFACT` 두 행의 `AUC_VALID`는 등록 값 그대로(기존 0.6071, 대안 0.6554)이고 `AUC_TEST`는 비어 있으며, 같은 라벨 AUC는 연체 라벨 기존 0.6047 / 대안 0.6078, 비금융 효과 라벨 기존 0.608(0.6080) / 대안 0.6591로 나왔다. `JSON_MERGEPATCH`는 로컬 Oracle에서 동작했다.
- 확인 못 함: 갱신 SQL을 다시 실행해도 같은 결과인지와 등록 SQL이 넣은 METRICS_JSON 기존 항목이 그대로 남았는지를 쿼리로 직접 보지는 않았다, 공용 DB 적용(Oracle 버전이 다를 수 있음), 서비스 연동과 시연 계정의 실제 점수, N-25 화면에서 읽는 모습.

## 다음 사람이 알아야 할 것
- 적용 순서: 범영 님이 0.2를 `MODEL_REGISTRY`·`MODEL_ARTIFACT`에 등록(`MODEL_EVAL_SAMPLE`의 모델 버전 FK) → 적재 SQL(한 번만) → 갱신 SQL. 공용 DB 실행은 DB 담당이 한다.
- 서비스 전환(0.2를 ACTIVE로)은 이 PR에 없다. 범영 님 PR #110(FP-237)으로 서비스가 불러온 묶음의 `meta.json` `model_version`을 실제 모델 버전으로 쓰게 되어서, 코드 상수(`config.MODEL_VERSION`)는 바꾸지 않는다(0.1 그대로). 0.2 등록은 PR #113, 전환은 `activate_model_lgbm_base_0_2.sql`이다(묶음 교체 후 바로 전환, 순서는 `fastapi_server/README.md`).
- 0.2 같은 라벨 AUC: 연체 라벨 기존 0.6047 / 대안 0.6078(차이 +0.0031, 시드별 -0.0170에서 +0.0188), 비금융 효과 라벨 기존 0.6080 / 대안 0.6591(+0.0511). 연체 라벨에서 대안 개선이 없는 것은 설계이고, 비금융 효과 라벨 차이는 설계한 효과가 반영된 값이다.
- 개인 점수가 0.1과 많이 다르다(기존 집단 VALID에서 39에서 43%가 30점 이상 변함, 현재 `CUT-0.1` 기준 등급 변경 22에서 27%). 시연 계정 점수를 전환 전에 다시 확인한다.
- 결측 처리(신용 이력 없음)는 **(a) 지금처럼 그대로 두는 것으로 임시 결정**했다(11/20, 재욱·범영 님 의견, 팀 이의가 없으면 확정, D-31): 모델 0.2는 카드 사용률·연체 건수 null을 0과 같게 읽는다. 한계는 "정보 없음"이 사용률 10%까지와 같은 점수라 약간 유리하다는 점이다(범영 님 사례에서 null·0%·10%가 모두 680점, 95%는 672점).
- 로그 파일명의 작성자 약어 `cjw`는 제안이다.
